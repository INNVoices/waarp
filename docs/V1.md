# Waarp 1.0.0 · code acceptance

Windows and Android share a release number and separate native engines. Existing profile formats, Android package IDs and the production signing certificate are retained. The maintainer reported about six hours of desktop use, including restarts, and stable Android use before this cleanup.

| Responsibility | Windows | Android |
| --- | --- | --- |
| Interface | React renderer in `src/renderer` | Kotlin / Compose in `android/app/src/main/java/local/waarp/android/ui` |
| Platform boundary | Electron preload and main process in `src/preload` and `src/main` | Android VPN service in `service/`, native lifecycle in `core/` |
| Policy and state | Route models in `src/shared`, application state and engine supervision in `src/main` | Models, imports and persistence in `data/` |
| Native engine | sing-box **1.14.2-lx.11** and Cronet, [hashes](../engine/integrity.json) | libbox **1.14.4-lx.35-waarp.2**, [source lock](../android/native-source.json), [hashes by ABI](../android/app/src/main/res/raw/engine_integrity.json) |
| Distribution | Portable Windows x64 EXE | Separate ARM64, ARM32 and x86_64 APKs. Version code **7**. |

## Build changes

The Windows builder now reads Android's engine from `android/engine/libbox.aar.xz` in Git (68,015,152 bytes). Python streams it into a temporary file, checks the uncompressed size and SHA-256 and replaces the installed copy only after verification. Gradle also verifies the AAR. The source rebuild recipe and dependency notices remain available. The SDK platform and Build Tools require about 125 MB of initial downloads in addition to Gradle and libraries.

Desktop builds install the lockfile with npm cache reuse, including when an older node_modules directory already exists. Desktop packaging no longer force-stops a running copy of Waarp or deletes older portable executables before building. Portable engine verification checks the cached binary and DLL against the application's shipped manifest. Local APK staging requires each declared ABI exactly once. The batch entry point returns the underlying build status.

## Evidence and limits

- Windows typecheck and repository checks passed. **64/64** offline suites finished successfully, with the opt-in native continuity scenario skipped. Portable packaging checks inspect the actual ASAR, executable, engine hashes and distributed notices.
- Android JVM tests on Windows passed **204/204**. TLS fixtures set their intended localhost name explicitly. On a filesystem without POSIX permissions the routing-file fixture checks that initialization fails before it can write route files.
- Both clients include 18 translated locales plus Russian. Packaging checks found all 36 desktop language chunks (main process and renderer) and all 18 matching source assets in each Android APK. Browser fixtures exercised translated navigation, regional Chinese selection and right-to-left document direction.
- All three debug and all three unsigned release APKs passed static verification. The checks inspect the manifest, package identity, native library hashes, signature status, ELF alignment and ZIP layout. The debug package ID is `local.waarp.android.debug`. Production updates require a release APK matching [the original certificate](../android/release-signing.json).
- The earlier disposable Windows runner reported a child-exit timeout on cycle 20. The process had already been asked to terminate. That record does not identify the cause. The earlier evidence is kept [with the original log](screenshots/preview-r6/native-failure-excerpt.log). No new live VPN, stress, emulator or device run was part of this code acceptance.
