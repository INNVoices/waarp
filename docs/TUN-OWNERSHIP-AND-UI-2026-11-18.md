# Waarp: управление TUN и UI на больших библиотеках — аудит 18.11.2026

**Скоуп:** Windows и Android, продолжение [ROUTE-AND-CONNECTION-AUDIT](ROUTE-AND-CONNECTION-AUDIT-2026-11-18.md). Источник замечаний — три скриншота владельца: большое число серверов на странице Google Chrome, список подключений, легенда диагностики. Код этого прохода находится в текущем `main`. Нативные ядра/пользовательские ключи/серверные настройки не менялись. Это RC-исправления, не утверждение о завершённой ручной приёмке на всех устройствах.

## Контракт владельца

1. **Главный переключатель — единственный обычный владелец ON/OFF.** Изменение маршрута, домена, приложения, группы, порядка, названия, сервера, резерва, служебного пути, DNS, параметров протокола не должно само переводить действующий TUN через OFF/ON.
2. **Первый выбор маршрута из idle:** если главный переключатель открыт, но TUN физически не нужен и не запущен, выбор профиля, которому уже требуется TUN, показывает явный диалог **«Включить VPN»**. Отказ сохраняет исходные правила; одобрение выполняет стандартную preflight-проверку с тем же owner/revision.
3. **Горячее изменение:** при совместимой загруженной топологии применяется через подтверждение native rule_set/selectors; меняются только затронутые соединения. Не требовать диалог и не скрывать фактическую ошибку.
4. **Структурное изменение:** новый нативный профиль, другие ключи/транспорт, предел слотов или несовместимая топология — **до любого stop/pause** необходим явный диалог с последствиями. Отмена — старое состояние и старое применённое правило. Одобрение действует лишь на ту же текущую master-ревизию/session-generation.
5. **Ошибка и отмена:** недоставленный ACK, отказ проверки безопасности, stale consent, невозможность отката, гонка с OFF — не сигнал к автоматическому restart. Прежний TUN сохраняется; ошибка видна, fail-closed защита остаётся.
6. **Системные исключения:** явный пользовательский OFF, закрытие процесса, ОС (сбой VPN-службы или сетевого адаптера), зарегистрированный Always-on/auto-connect, аварийный fail-closed security stop и восстановление после сна не равны изменению карточки. Физическое состояние TUN в этих событиях контролируется ОС и системой защиты, поэтому обещание «TUN никогда не меняется без клика» невозможно реализовать буквально. Для штатных **мутаций данных** правило 1 строгое. Подмена системной блокировки на небезопасный Direct недопустима.

### Windows: что обнаружено и закрыто

- Раньше `createApply` умел **сам запускать idle TUN**, а на `blocked` сам останавливал работающий. Теперь для запуска требуется активное согласие; блокирующая правка отменяется без скрытого OFF.
- `ConnectionControl.reconnect` при превращении всех маршрутов в Direct вызывал idle cleanup и останавливал TUN. Теперь ON сохраняется, а ошибочный/stopping native state не выдаётся за успешный OFF.
- В `settings` structural fallback вызывал `master.reconnect(restart:true)` без разрешения. Теперь сначала `engine.applyLive`, при incompatibility — системный диалог; отмена откатывает неуспевшие примениться настройки.
- `profile:replace/remove` мог вызвать `engine.stop()` до сохранения. Предупреждение показывается **до** остановки; inactive удаление не трогает core.
- `tune:apply/reset` раньше запускали forced restart после записи. Теперь consent до сохранения активной настройки.
- Background network-tune update и refresh служебных списков раньше могли делать silent restart. Теперь уведомление без перезапуска, с явным требованием осознанного выключения/включения для несовместимого изменения.
- `net:reset` на живом master больше не выключает VPN тайно: предлагает сначала вручную OFF.
- Результат несостоявшейся живой операции не объявляется успешно применённым. Сценарии «подтверждение от одного файла вместо всех» покрыты существующим guarded-apply/ACK-контрактом.

### Android: что обнаружено и закрыто

- В `MobileRepository.edit` несовместимая правка автоматически шла по `pauseForUpdate → OFF → resumeAfterUpdate`. Теперь перед паузой проводится согласование через `MobileEvent.RestartApproval` → `MainActivity` `AlertDialog`. Если Activity отсутствует, отказано или истёк таймаут — **не паузить**.
- Согласие действует только для прежнего intent generation, того же native session generation и действующего ON. Пользовательский OFF, новый ON или смена сессии делают прошлый ответ недействительным.
- `pauseForUpdate` возвращающий `null` раньше мог пропустить остановку и продолжить запись новой структуры; теперь это явная ошибка до публикации.
- `recover` при живом/запрошенном VPN больше не выключает его в обход главного переключателя.
- Совместимые изменения продолжают идти через `LiveRoutingFiles.apply` с пофайловыми witness/ACK и защищённым откатом. Это **не** обещание, что произвольные новые native outbounds возможно добавить без перезапуска.

## UI/UX — малые, адресные изменения

**Скриншот Google Chrome.** Главный и резервный список под маршрутом теперь показывают по **8 вариантов**, затем `Показать ещё` с добавлением по 16. Длинный список прокручивается; поиск фильтрует название, адрес и протокол. Текущий выбор, Direct и Auto закреплены в доступной части. Это изменение **только представления** и не отправляет команды VPN. Больше нет искусственного потолка 100 серверов.

**Типографика.** Название сервера и тип/адрес не борются за одну строку с `проверяю` и ping: отдельная область метрики с максимальной шириной, однострочная обрезка с tooltip. Карту соединений и подписи в диагностике защищают `min-width:0`, `ellipsis` и responsive grid. Существующие страницы, цвета, панели и навигация сохранены.

**Проверка масштаба.** Браузерный regression-test загружает 160 искусственных названий с длинными токенами, проверяет начальный размер главного/резервного списка, фильтрацию, последовательное раскрытие, отсутствие горизонтального overflow при ширине 1240/900/720/620 и отсутствие `selectRoute` от UI-фильтрации. Полную визуальную оценку всех реальных профилей он не заменяет.

## Регрессии и границы доказательств

- Настольные unit/integration: контракт `createApply`, контроллер ON/OFF, stale-revision, live guard/rollback, реальный `Engine.applyLive` в изолированном тесте. Запущенные CI офлайн-наборы прошли **46/46**; текущий окончательный commit надо сверять по отдельному CI-run.
- Android JVM: новые `StructuralRestartApprovalTest` (не требуется / нет UI / отказ / новый owner после промпта). Стандартные test/lint/build workflow запускаются для изменений Kotlin; **готовую APK считать проверенной только после конкретного результата job**.
- Windows browser: длинные имена, фильтрация, страницы, ширины и статусные подписи. Финальная browser проверка и нативные циклы TUN должны быть связаны с **актуальным commit**, а не с более ранним RC.
- Нет доступа к реальному телефону/оператору пользователя и настоящему Windows TUN на его машине. Результат локального эмулятора/CI не означает стабильность конкретной мобильной сети.
- GitHub Actions ранее возвращал ошибку **Artifact storage quota has been hit** при выгрузке отчётов и сборок, даже когда функциональные тесты проходили. Общий зелёный статус CI отдельно блокирует аудит pinned `picomatch` в build toolchain; не отключать проверку для получения зелёной галочки.

## Ручная приёмка владельца (после сборки из текущего main)

1. Включить master один раз; зафиксировать PID ядра/имя адаптера и соседнее TCP-соединение (Chrome/Telegram или загрузка).
2. По очереди: Direct → загруженный профиль → другой → Auto/группа → удалить выключенную карточку → отключить последнюю → удалить последнюю → добавить её снова. Статус master, PID, TUN и соседний TCP должны сохраняться.
3. Переключить на реально **незагруженный** профиль или изменить ключи: должен появиться диалог **до остановки**. Отмена должна оставить те же PID, TUN, профили и применённые маршруты; согласие — единичный контролируемый restart.
4. Одновременно с открытым диалогом выключить master: просроченное согласие не должно запускать новый core. Повторить для удаления, групп, DNS и резервов.
5. При master-open и отсутствии TUN выбрать маршрут, требующий core: должно появиться `Включить VPN`; без одобрения запускать TUN нельзя.
6. На Android повторить это на физическом телефоне и проверить VpnService session ID, переключения Wi-Fi/LTE, выход из приложения/возврат, отмену и системный Always-on.
7. Проверить длинные/корейские/без пробелов названия в масштабах 100%/125%/150%, клавиатуру, screen reader и выбранный сервер вне первых 100.

**Не объявлять production DONE до физической приёмки и обработки выявленных исключений.**
