# Переиспользование open source: проверенные основы и пределы

**Дата проверки:** 18 ноября 2026 года. **Статус:** подготовка; реализация ожидает отдельной команды владельца. Источники кода прочитаны, зависимости не добавлялись, нативные эксперименты не выполнялись.

Документ дополняет [срез кода](01-CODE-BASELINE.md), [техническое ТЗ](04-TECHNICAL-SPEC.md) и [контракт Atlas](06-ATLAS-DATA-COMMUNITY.md). Все репозитории ниже проверены по первичным исходникам или официальной документации. Точные SHA, файлы, лицензии и пределы выводов сохранены в [sources-oss.json](sources-oss.json). Текущая ветка upstream и исходники фактически упакованного ядра — разные источники; возможности одной не приписываются другому.

## 1. Решение для ближайшей реализации

**Сначала использовать уже закреплённые ядра и логику Waarp. Единственные новые крупные зависимости, предварительно выбранные для ближайшего этапа, — картографические библиотеки MapLibre.** Их добавление всё равно зависит от ограниченного эксперимента на реальных платформах.

| Направление | Предпочтительная основа | Способ использования | Что остаётся работой Waarp |
|---|---|---|---|
| Подбор пути и объяснение отказа | Имеющиеся probe/evidence/network-memory/Auto; закреплённый sing-box-lx | Сохранить одного владельца измерений и выбора; проверить доступность существующих диагностических API ядра | Контекст приложения, лимиты, достоверность пути, понятный результат, отмена, защита от устаревшего результата |
| Меньше разрывов | Имеющийся selector, работники и управление TUN | Разделить выбор для новых потоков и завершение старых; проверить точную семантику прерывания | Причина переключения, сохранение нужного старого worker, ограниченный drain, отключение по запрету/удалению |
| Локальный Atlas, Windows | MapLibre GL JS + локальная геометрия Natural Earth | Изолированный лениво загружаемый компонент; встроенные слои точек/линий/кластеров | Связь с существующим каталогом и выбором, достоверная география, состояние неизвестности, доступный список |
| Локальный Atlas, Android | MapLibre Native Android + та же модель данных карты | Нативный MapView, встроенный в существующий Compose-экран, с полным lifecycle | Общая семантика выбора при сохранении нативной навигации и жестов |
| Первые профили приложений | Имеющиеся presets/rules; ограниченные данные из проверенных domain catalogs | Небольшие встроенные описания и явно закреплённые наборы доменов | Требования приложения, безопасные проверки, смысл рекомендации; сопоставление процесса/package |
| Дальнейшие алгоритмы | Mihomo health-check, Tailscale netcheck/magicsock, методика OONI | Источник архитектурных решений и сравнения | Реализация поверх существующего контура Waarp, без импорта чужого приложения целиком |

Не включать в ближайший runtime отдельные OONI Probe, NDT7, Cloudflare speedtest, второй proxy core или deck.gl. Их полезность рассмотрена ниже; ни один из них не закрывает пригодность произвольному приложению одним подключением библиотеки.

## 2. Какая версия ядра действительно используется

Базовый срез Waarp соответствует дереву main **f66e5def3d689837db010c3453086a832c701fcc**. Источники pin: [engine/SOURCE.md](../../../engine/SOURCE.md), [scripts/engine.mjs](../../../scripts/engine.mjs), [android/native-source.json](../../../android/native-source.json). После завершения соседней работы эти значения должны быть сверены ещё раз задачей WN-00.

| Характеристика | Windows | Android |
|---|---|---|
| Версия | 1.14.2-lx.11 | 1.14.4-lx.35-waarp.2 |
| Исходный commit sing-box-lx | [3d3d3db3a2ccef3b1a8eb71b831ed2461c54b94d][lx-win] | [f1bac271853eaf13398ce1030c948aebc3aed2e1][lx-android] |
| Связь с приложением | Отдельный процесс и генерируемая конфигурация, по собственному SOURCE.md | Нативная AAR; собственные DNS transient-reset и WireGuard GSO-retry patch |
| least_test | Есть в pinned source | Есть в pinned source |
| round_robin, balancer.sticky_hash | Есть в pinned source | Есть в pinned source |

| common/networkquality и STUN | Есть в pinned source | Есть в pinned source |
| Новое staged ConnectionTest через libbox CommandClient | В desktop pin этого набора файлов нет | Есть; доступность из фактической AAR и работа через текущий сервис ещё не проверены |

Проверка основана на option/group.go, protocol/group/urltest_balance_lx.go и документации **внутри этих SHA**, а не на сегодняшнем README. Нельзя обещать Windows режим failover из более свежего Android-ядра. Наличие mode в исходниках также не означает, что Waarp сегодня его использует.

В существующей конфигурации Waarp группы строятся как selector и выбираются собственными probe rounds: src/main/awg.ts прямо объясняет эту границу; src/main/engine.ts владеет групповыми решениями. Добавить одновременно независимый URLTest scheduler означало бы создать двух владельцев выбора. Ближайший план этого не предусматривает. Точные места и последствия — в [01-CODE-BASELINE.md](01-CODE-BASELINE.md).

### 2.1. Selector и сохранение соединений

В обеих закреплённых версиях SelectOutbound вызывает interruptGroup.Interrupt с флагом interruptExternalConnections. Документация ядра отделяет входящие пользовательские соединения от внутренних: настройка interrupt_exist_connections влияет на первые; внутренние соединения при переключении прерываются всегда. См. [Windows selector][selector-win] и [Android selector][selector-android].

Практическое следствие: **false — кандидат на сохранение существующих внешних потоков, но не готовая бесшовность**. В Waarp дополнительно есть собственное закрытие затронутых соединений и очистка workers; сохранённый socket бесполезен, если его worker уже уничтожен. DNS и внутренние проверки также нельзя считать сохранёнными только по этому флагу. Механика drain и причины обязательного закрытия определены в техническом ТЗ.

Смена селектора не переносит старую TCP-сессию на другой внешний IP. Даже если новый путь уже подготовлен, сохранение пользовательской сессии зависит от живого старого пути и поведения конкретного протокола/приложения. При полном исчезновении старого пути ближайшая цель — быстрое и предсказуемое восстановление.

### 2.2. URLTest, balancing и sticky — не измерение приложения

В pinned common/urltest/urltest.go измерение открывает **TCP** через выбранный dialer, затем делает **HTTP HEAD**; перенаправления автоматически не проходят. Такой результат описывает конкретную проверку URL. Он не подтверждает UDP-ответ, потери игровых пакетов, успешную авторизацию приложения или пригодность для звонка. [Исходник URLTest][urltest-core]

round_robin выбирает узел один раз на новое соединение или packet connection. В sticky-ключе могут участвовать process/domain; отсутствующие данные дают пустые компоненты, поэтому тест должен учитывать наличие process/package metadata. Привязка удерживает поток на выбранном узле и не обеспечивает миграцию при его смерти. Для обычного пользователя эти параметры не нужны как набор переключателей. [Windows balancer][balancer-win], [Android mode documentation][urltest-android]

## 3. Сильнейшая возможность для переиспользования — уже внутри ядра

До добавления внешней системы измерений нужно проверить два существующих набора API. Это проверенные **исходники**, а не утверждение о готовом подключении из UI.

### 3.1. Android: активный ConnectionTest с этапами

В Android pin найдены:

- [experimental/libbox/command_client_conntest_lx.go][conn-client]: CommandClient.StartConnectionTest, поток стадий OnStage, финальный OnResult; OnError относится к поломке самого потока. Отмена сессии прекращает последующие callbacks.
- [experimental/libbox/command_types_conntest_lx.go][conn-types]: SetOutboundTag для конкретного узла, SetLink, глубина проверки, network, timeout, max bytes, app-like DNS и входные метаданные маршрутизации.
- [daemon/started_service_conntest_lx.go][conn-daemon]: выполнение через узел или router, стадии соединения/HTTP и формирование результата.

Это близко к нужному «детективу»: вместо разбора строки «не работает» адаптер может перевести структурированные стадии в существующие evidence/finding Waarp. Один отчёт пригоден и для выбора пути, и для объяснения неудачи. Запрос активный: он создаёт реальный трафик и может разбудить idle endpoint. Исходник прямо предусматривает явное действие пользователя.

**Границы, которые обязательны для адаптера:**

| Возможность в API | Что можно утверждать после успешной проверки | Что пока утверждать нельзя |
|---|---|---|
| SetOutboundTag | Тест запросил конкретный outbound; фактическое исполнение нужно привязать к этому tag/generation | Что все потоки выбранного приложения уже идут туда |
| PackageName / UID / ProcessPath | Маршрутизация проверена с заданными метаданными | Что это захваченная реальная сессия установленного приложения |
| HTTP stage | Получен результат конкретного URL на конкретной глубине | Что пройдены redirect, login, DRM, игровой handshake или всё приложение |
| UDP runPacketRoute | Проверена маршрутизация пустого packet pipe и ошибки маршрута/первого участка | Что сервер отвечает по UDP, измерены RTT/loss/jitter или игровой трафик работает |
| Stage/result attrs | Есть материал для локальной диагностики | Что все поля допустимо хранить, показывать как факт о провайдере или публиковать |

UDP-ограничение особенно важно: runPacketRoute создаёт packet pipe **без полезной нагрузки**. Из него нельзя получить потери или пригодность звонку. Для таких выводов нужен разрешённый ответчик, реальный обмен и ясное описание измеряемого endpoint. Если такого доказательства нет, поле остаётся unknown.

При обёртке нужно убрать из обычного UI внутренние теги и сырые trace; из экспорта — заголовки, body, секреты, полные личные URL и прочие избыточные поля. Проверка URL без follow-redirect должна показывать собственный смысл, а не превращать redirect или 403 автоматически в «путь не работает».

Доступность проверяется отдельно: наличие with_lx_command в android/native-source.json ещё не подтверждает Java/Kotlin exports, совместимость текущего CommandClient и правильную привязку socket к сети Android при включённом VPN. До этого gate функция не помечается ready.

### 3.2. NetworkQuality: задержка при нагрузке и пропускная способность

В обоих pins есть [common/networkquality/networkquality.go][networkquality]: idle latency, download/upload capacity, RPM для направлений и отдельные признаки точности. Это пригодная основа для специальной расширенной проверки отзывчивости сети при нагрузке. По умолчанию источник конфигурации — Apple mensura; наличие такого default не является решением Waarp обращаться туда автоматически.

Есть два разных способа вызова:

| Путь | Проверенное свойство исходника | Следствие |
|---|---|---|
| [cmd_api_networkquality.go][nq-api] | CLI принимает outbound/-o и передаёт OutboundTag в daemon request | Возможен тест явно выбранного пути после проверки доступного daemon API и фактического исполнения |
| [cmd_tools_networkquality.go][nq-tools] | Создаёт dialer для указанного outbound и передаёт его HTTP/HTTP3 клиентам | Подходящий reference для явного пути; отдельный процесс/конфигурация может не совпадать с живой сессией Waarp |
| [libbox/networkquality.go][nq-libbox] | Standalone helper создаёт NewHTTPClient(nil) и HTTP3 factory с nil dialer | Нельзя подписывать результат «через сервер X» только потому, что этот сервер выбран в UI |
| [libbox/stun.go][stun-libbox] | Standalone helper не принимает outbound tag | NAT/STUN-наблюдение нельзя автоматически отнести к нужному маршруту |

Не запускать capacity/load-test при открытии карты, при каждом auto round или во время игры по умолчанию. Он способен сам занять полосу и изменить измеряемую задержку. Нужны отдельное действие, описание трафика, остановка, ограничения по сети/энергии, разрешённые measurement endpoints и результат с точностью. Выбор внешнего сервиса и условия его использования пока не завершены; тест может остаться недоступным до такого решения.

У текущего desktop API может быть только уже используемый Clash endpoint; наличие нового daemon API в исходниках не даёт права молча включить дополнительный сервис. Эксперимент должен подтвердить минимальный поддерживаемый путь интеграции. Отдельный диагностический subprocess не должен становиться владельцем TUN.

### 4.1. Почему здесь нужна точная ветка

У MetaCubeX/mihomo на момент проверки default branch main содержала другой Python-проект. Нужный сетевой код найден в **ветке Meta**, срез 0455d0d28c4526937380505153e65a843d8612e8. Проверены [provider/healthcheck.go][mihomo-health] и [outboundgroup/urltest.go][mihomo-urltest], а также LICENSE/README из того же SHA. MIT badge/метаданные default branch нельзя переносить на эти файлы. Этот пример — причина фиксировать в реестре и commit, и path, а не только URL репозитория.

Из Mihomo полезны организация ограниченной очереди проверок, lazy behavior, устранение параллельных одинаковых задач и удержание выбора с tolerance. Это рекомендации к алгоритму Waarp, не предложение копировать GPL-файлы в Apache-код без отдельного решения.

### 4.2. Где именно заканчивается полезность Tailscale

netcheck строит картину UDP/NAT/доступности relay с учётом своей инфраструктуры; magicsock сочетает прямые пути и relay для своих peers. Его механика объясняет, как не считать единичную удачу устойчивой связью и как менять предпочтение пути. Но сохранение endpoint identity внутри этой системы нельзя обещать произвольному VPN-серверу.

В Android build tags уже есть with_tailscale. Это не означает наличия независимого публичного netcheck API для всех узлов Waarp и не является основанием включать Tailscale control plane. Ближайший путь — собственная модель network epoch и явные наблюдения поверх уже имеющихся sockets/core.

### 4.3. Почему не брать целиком OONI / speedtest

Их тестовые endpoint, способ регистрации результата и модель продукта отличаются от локального клиента маршрутизации. Для «почему это приложение не работает» сначала нужен корректно выбранный путь, target и интерпретация исхода. Новый измерительный пакет сам эти три решения не делает.

Из OONI разумно брать структуру проверки и осторожное разделение наблюдения и причины. Успешный TCP, сбой TLS, неожиданный HTTP и DNS-расхождение — разные факты; они не доказывают виновника сами по себе. Полный engine и его публикация измерений в ближайший объём не входят. [Официальная спецификация Web Connectivity][ooni-webconnectivity]

Cloudflare README отдельно описывает отправку результатов и TURN credentials для loss. У M-Lab policy опубликованные измерения хранятся бессрочно. Такие службы можно предлагать только как явно описанную отдельную проверку после выбора условий; они не являются незаметной частью Auto или Atlas.

## 5. Atlas: готовый движок, локальная основа, честная география

Для первого выпуска предлагается **Natural Earth 1:110m + собственный локальный стиль MapLibre**, без обязательного CDN, геокодера и tile server. Низкая детализация подходит для обзорной карты серверов; улицы не нужны. Точный набор, конверсия и упрощение геометрии будут закреплены вместе с размером и hash после старта. Использовать чужой demo style из quickstart в продукте не следует: он может подтянуть удалённые тайлы, glyphs, sprites и другой источник данных.

MapLibre даёт слои и взаимодействие с картой; он не предоставляет автоматически данные о местоположении узлов, право на сторонние тайлы или бесконечную бесплатную инфраструктуру. Отдельно фиксируются лицензии/условия геометрии, glyphs/fonts, sprites/icons, optional GeoIP и любого будущего tile provider. Для Natural Earth attribution не обязателен по официальным terms, но источник разумно сохранить в notices и экране данных.

Готовые MapLibre GeoJSON source/layers позволяют сначала обойтись без deck.gl. Дуги логических связей можно подготовить как линии; их нельзя называть измеренными hop-маршрутами. Если позднее появятся объёмы или взаимодействия, которые базовые слои не выдерживают, deck.gl оценивается по конкретному профилю производительности.

На Android официальный quickstart показывает MapView и передачу lifecycle. Встраивание через Compose AndroidView — проектное решение для Waarp, а не обещание готовой совместимости без проверки. Не вводить ради карты React Native, Flutter или второй UI framework.

**География и метрики поступают из модели Waarp.** Название сервера с флагом или городом не доказывает координаты. Недостоверная или отсутствующая география должна оставаться неопределённой, а не превращаться в точный pin в центре города. Линия на карте — логическая связь; задержка — наблюдение конкретной проверки с возрастом. Подробный контракт, offline и возможное community-продолжение описаны в [06-ATLAS-DATA-COMMUNITY.md](06-ATLAS-DATA-COMMUNITY.md).

## 6. Профили приложений и rule-set: разные уровни

Официальный [source format sing-box][rules-format] задаёт version и список headless rules, компилируемых в бинарный rule-set. [Headless rules][rules-headless] описывают условия сопоставления. Набор доменов — вход для сопоставления трафика, **не готовый профиль качества приложения**.

Для ближайшего этапа нужны три небольшие части:

1. **Identity:** существующий процесс/package и, при необходимости, ограниченный список доменов. Данные каталога не заменяют реальное сопоставление процесса.
2. **Requirements:** проверенные требования приложения и предпочтения пользователя. Не выводить «нужен UDP» просто из категории games.
3. **Probe descriptor:** разрешённая проверка, target, бюджет, трактовка результата и срок актуальности. Это данные фиксированной схемы, а не исполняемый JS/Lua или произвольный config ядра.

Собственные presets Waarp остаются основой. Первый импорт каталога должен быть маленьким и проверяемым: точный upstream commit, выбранные категории, их includes, преобразование в поддерживаемый формат и notices. Не тянуть весь каталог, если нужен один профиль; не выполнять удалённый конфиг и не переносить из него DNS, private endpoints или команды.

Семантику версии rule-set подтверждать **закреплённым бинарником каждого ядра**. Текущая страница документации содержит несколько поколений формата и сама по себе не доказывает успешный compile/load в shipped runtime. Если общего поддержанного формата нет, хранить нейтральные данные профиля и отдельно компилировать для каждой платформы.

## 7. Лицензии: что проверено и что ещё требуется

В Waarp собственная desktop-часть объявляет Apache-2.0, Android-часть — GPL-3.0-or-later; desktop SOURCE.md описывает отдельный процесс ядра. У sing-box-lx LICENSE содержит GPL-3.0-or-later и дополнительное условие о названии/ассоциации. Это **описание исходных фактов, не юридическое заключение о любой будущей комбинации**.

При непосредственном добавлении новой зависимости нужно:

- закрепить exact release/artifact и полный набор транзитивных notices; не ограничиваться badge репозитория;
- различать использование отдельной программы, линковку библиотеки, перенос конкретного исходника и использование опубликованной методики;
- сохранить существующие corresponding-source/manifest процессы ядра, особенно Android patches и ABI;
- отдельно записать происхождение и условия картографических данных, правил, шрифтов, иконок и внешней службы;
- при изменении ядра или копировании чужого кода повторно проверить условия именно затронутых файлов.

Исследование не переносит GPL-код в Apache-часть и не меняет лицензии Waarp. При reference-only подходе допускается изучение архитектурной идеи; это не разрешение стереть notices при последующем копировании реализации.

## 8. Ограниченные эксперименты после команды на старт

Все пункты ниже имеют статус **WAIT_OWNER_START**. Их цель — снять конкретную неопределённость; отсутствие результата не компенсируется заменой всего ядра.

| ID | Что проверить | Минимальный опыт | Gate / решение |
|---|---|---|---|
| OSS-S1 | ConnectionTest реально доступен Android | Просмотр exports фактической AAR; один запрос через текущий сервис к разрешённому endpoint с конкретным outbound, отменой и сменой network epoch | Либо получены корректные стадии/отмена/идентичность пути, либо используем существующие probes; feature не объявляется готовой по одному Go-файлу |
| OSS-S2 | Доступен ли NetworkQuality через нужный путь | Help/exports фактических артефактов; один разрешённый тест с доказанным outbound и наблюдением трафика | Нет доказательства пути — метрика не относится к узлу. Нет согласованного endpoint policy — тест не включается в продукт |
| OSS-S3 | Selector false и старый worker сохраняют внешние потоки | Контролируемые долгий TCP и двусторонний UDP; обычная смена, деградация, отзыв, master OFF; наблюдать влияние собственного close/trim | Для каждого события зафиксированы сохранение/разрыв и причина. Internal DNS отдельно. Без утверждений о миграции после смерти сервера |
| OSS-S4 | MapLibre работает локально в текущих оболочках | Локальный стиль/геометрия; каталог контрольного размера из плана приёмки; открыть/закрыть, resize/rotation, resume, клавиатура, fallback list | Нет неожиданных сетевых обращений, сохранены выбор/фокус/скролл, нет продолжающего работать скрытого renderer; размеры и ресурсы измерены |
| OSS-S5 | Профили и каталоги компилируются предсказуемо | Один небольшой профиль на обеих платформах, закреплённые source data, положительные/отрицательные identity matches | Нет произвольного исполнения, совпадения объяснимы, pinned core принимает формат; неизвестные требования остаются unknown |
| OSS-S6 | Если понадобится UDP QoE, есть настоящий ответчик | Один согласованный responder/протокол с sequence/timeouts, лимитом и путём через конкретный outbound | Получены реальные response/loss/jitter и описана применимость. Route-only / STUN не подменяют игровой трафик; иначе пункт отложен |

### Соответствие единому плану работ

Основная очередь и критерии приёмки находятся в [05-PLAN-AND-ACCEPTANCE.md](05-PLAN-AND-ACCEPTANCE.md). Обозначения OSS-S1…S6 — ссылки на технические подробности переиспользования, **не второй backlog и не дополнительные обязательные задачи WN-01**. Одно наблюдение и один отчёт закрывают соответствующие пункты обоих документов.

| Подробность здесь | Место в едином плане | Граница соответствия |
|---|---|---|
| OSS-S1 | WN-01: CAP-01 и CAP-04 | Экспорты/конкретный outbound относятся к CAP-01; новый public candidate при ON, отсутствие второго TUN и отмена — к CAP-04. Успех одного вызова не закрывает оба сценария автоматически |
| OSS-S2 | WN-01: сведения об API из CAP-01/CAP-04; WN-02: явный подробный тест | NetworkQuality не является отдельным обязательным CAP. В WN-01 фиксируется доступность и граница пути; тест с нагрузкой выполняется только если он включён в объём WN-02 и выбран допустимый endpoint |
| OSS-S3 | WN-01: CAP-02 и CAP-03; затем WN-05 | CAP-02 проверяет selector на каждом pin, CAP-03 — живой sidecar/worker. Сценарии причин переключения и прекращения недопустимого пути входят в WN-05 |
| OSS-S4 | WN-01: CAP-06 и картографическая часть CAP-07; затем WN-03/WN-06 | CAP-06 отвечает за достаточность MapLibre, CAP-07 — минимальную локальную географию; GeoIP/reader проверяется по контракту 06. Полные lifecycle/UI-сценарии входят в приёмку карты |
| OSS-S5 | WN-04 и WN-07 | Проверка небольшого профиля/формата и воспроизводимого вклада. Отдельного CAP-08 или обязательной новой платформы профилей не создаёт |
| OSS-S6 | WN-01: CAP-05; затем применимые проверки WN-04 | Реальная передача через контролируемый UDP responder и доказательство пути. При отсутствии результата используется fallback CAP-05: «не проверено» |

Все эксперименты входят в подготовленный план и ожидают команды на начало реализации. После старта результаты добавляются к [плану приёмки](05-PLAN-AND-ACCEPTANCE.md) и сопоставляются с обновлённым main. Отдельные сверхмалые цифры времени apply не заменяют пользовательскую непрерывность игры, загрузки или звонка.

## 9. Оставшиеся решения

Ниже перечислены открытые вопросы реализации, а не просьба немедленно отвлечь владельца:

- какие диагностические команды и exports есть в **фактических** Windows EXE / Android AAR; присутствия исходников недостаточно;
- как доказать Direct при включённом TUN: socket через системный маршрут не всегда означает обход VPN;
- какой measurement endpoint разрешён для HTTP/UDP/load-test и какие у него условия; сейчас публичная инфраструктура не утверждена;
- какие published MapLibre artifacts поддерживают целевые ABI/API/16 KB требования и какой их фактический прирост размера;
- точный Natural Earth asset/version/hash, локальные fonts/glyphs и бюджет геометрии;
- какие первые приложения и domain categories дают полезный профиль, подтверждённый на реальных сценариях;
- где сохранение сессии ограничено протоколом/сервером и когда допустим только быстрый reconnect.

Достаточная подготовка сейчас: конкретный малый стек выбран, версии и свойства проверены, ложные равенства устранены, неизвестное имеет отдельный gate. Реализация ждёт команды владельца.
