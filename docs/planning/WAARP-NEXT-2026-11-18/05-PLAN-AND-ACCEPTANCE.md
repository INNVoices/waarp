# План реализации и проверяемая приёмка

**Статус всех задач:** WAIT_OWNER_START. Это подготовленная очередь, не команда запускать разработку. После отдельного старта владельцем применить WN-00, затем работать небольшими завершёнными изменениями с сохранением текущего UX.

## 1. Единые правила

- Один владелец изменения native runtime. Подбор, карта и диагностика не запускают собственные ON/OFF/restart.
- Один общий источник наблюдений. Продуктовые сценарии используют существующие checker, diagnosis, evidence, memory и repository/core adapters.
- Windows и Android имеют разные engine pin и API. Поведение согласуется на уровне пользовательского контракта; внутренние реализации могут отличаться.
- Работающий режим выпускается вместе с реальным UX: корректные состояния, отмена, длинные тексты, touch/keyboard, offline и явные границы измерений.
- Новое поле или очередь не создаётся, пока не проверено, что существующий тип/владелец не подходит. Не добавлять общую «платформу расширений» ради нескольких профилей.
- Не переписывать unrelated код и не ослаблять текущие release/stable gates. Перечень существующих проверок берётся из актуального main, не из старого отчёта.

## 3. WN-00 — сверка перед стартом

1. Прочитать текущий main, новые коммиты соседнего исполнителя и изменившиеся документы.
2. Сравнить с baseline.json: UI, apply, engine, compiler, checker, native locks и тесты.
3. Проверить текущую Android FormSheet/notifications, Windows ServerPicker и реальные доступные screenshots. Старый routing.png не считать текущим экраном.
4. Зафиксировать результаты уже идущего релиза отдельно. Текущий docs-корпус не устанавливает статус стабильности.
5. Прочитать новые AGENTS.md, если они появились, и текущие branch rules. Не обходить защиту.
6. Обновить только изменившиеся предположения данного ТЗ. Требования владельца и ожидание UI/UX сохраняются.

**Выход:** короткая таблица «без изменений / изменилось / влияет на задачу» с SHA. При продвижении main не надо повторять всё исследование: перечитать затронутые места.

## 4. WN-01 — ограниченные проверки, которые снимают риск

Это будущие эксперименты после разрешения на старт. В этой подготовке они не выполнялись.

| ID | Вопрос | Минимальная проверка | Решение при отрицательном ответе |
|---|---|---|---|
| CAP-01 | Экспортирован ли Android ConnectionTest в используемый AAR и доступен ли заданный outbound? | Прочитать фактическую сигнатуру, вызвать на разрешённой контрольной цели, сверить endpoint свидетелем на сервере | Использовать имеющийся путь измерений; не выдавать default dialer за per-outbound |
| CAP-02 | Сохраняет ли selector существующие TCP/UDP при soft update на каждом pin? | Два маршрута, длительные TCP + UDP, один переход с наблюдаемыми native PID/session и flows | Оставить консервативное hold-until-idle; не обещать native drain |
| CAP-03 | Что происходит при смене selector внутри sidecar/live-outbound? | То же соединение + новый поток + retained worker lifecycle | Удерживать/учитывать worker до завершения; при отсутствии API не освобождать его по таймеру как будто idle |
| CAP-04 | Можно ли измерить новый Android public candidate при ON без второго TUN? | Проверить фактический native per-outbound proxy/fetch/test API, redirect/IP/TLS policy и cancellation | Явная граница платформы; список и карта работают, проверка не останавливает VPN |
| CAP-05 | Какие UDP-проверки действительно посылают и получают данные через нужный путь? | Controlled responder и счётчики обоих концов | Показывать «не проверено»; не строить loss/jitter из HTTP или payload-less route test |
| CAP-06 | Достаточен ли MapLibre без deck.gl? | Документированный GeoJSON слой на 10k/2k синтетических несекретных узлах, local style, pan/zoom/select | Оптимизировать слои/кластеризацию и данные до добавления ещё одного рендера |
| CAP-07 | Каков минимальный локальный набор географии? | Natural Earth + версия GeoIP/reader: формат, размер, lookup, notices | Региональные группы и unknown; не делать GeoIP обязательным сетевым запросом |

Для каждой проверки сохранить: точный pin/API, вход, измеренную границу, результат, вывод и рабочий fallback. Один bounded experiment не должен перерасти в написание собственного транспортного ядра.

## 5. WN-02 — наблюдения и существующая диагностика

Развить текущие структуры, а не переносить приложение на новый runtime. Связать каждое наблюдение с целью, маршрутом, профилем, physical network, generation, временем, методом и числом наблюдений. Пользовательские операции имеют приоритет над фоновой проверкой; одинаковые запросы разделяют результат, если контекст одинаков.

Обязательно:

- Отменённое, вытесненное, не запущенное и неподдерживаемое измерение не считается отказом сервера.
- Смена сети, профиля или owner revision делает неподходящее доказательство неприменимым.
- Измерение и рекомендация не выполняют apply сами по себе.
- Фоновое чтение/карта используют кеш; не запускают отдельные бесконечные scanners.
- Целевой подбор одной карточки не перемещает общий g-auto остальных приложений.
- Подробный throughput/upload-тест остаётся явным действием; на мобильной/лимитной сети виден объём и можно отменить.
- Существующие ограничения числа checker, времени и кандидатов сохраняются, пока отдельное измерение не обосновало изменение.

**Приёмка:** один запрос, отмена, duplicate subscriber, смена сети, OFF и удаление профиля не дают позднего apply и не портят состояние другой карточки.

## 6. WN-03 — локальная карта

Порядок: общий read-model → локальная карта и unknown states → синхронизация со списком → desktop placement → Android native placement → visual/performance pass.

Первые screens должны быть продолжением текущего интерфейса: Windows внутри существующих Connections/ServerPicker, Android внутри Tunnels/route draft. Не добавлять отдельные глобальные Atlas/Autopilot/Detective вкладки.

**Приёмка:** сценарии AT-01–AT-10 ниже, offline, GPU failure, восстановление контекста, отсутствие сетевых изменений от browsing. Точность карты не должна зависеть от числа декоративных линий.

## 7. WN-04 — профили и объяснимый выбор

Начать с малого набора профилей требований: обычный веб-доступ, голос/интерактивный трафик, игра; большой transfer — отдельная явная проверка. Это классы требований, не обещание готового пакета для каждой игры.

Использовать существующие presets, lists и application matching. Расширение metadata содержит версию, источники rules, применимые проверочные методы, приоритеты и допустимую политику обновления. Личное подключение выбирает пользователь; профиль не импортирует серверы и не меняет permissions.

Критерий выбора сначала исключает недопустимые/непроверенные варианты, затем сравнивает сопоставимые результаты с достаточным качеством. Малую разницу не превращать в обязательное переключение. Нет уверенного улучшения — сохранить текущий путь и сообщить это коротко.

Не конвертировать произвольный TCP/UDP приложения в другой транспорт кнопкой. Отдельно учитывать транспорт приложения, перенос внутри туннеля и возможности сервера. Один открытый TCP socket не устанавливает пригодность голосовой UDP-сессии.

**Приёмка:** рекомендация воспроизводима по журналу наблюдений; одно объяснение с ограничением; неподдержанный UDP не даёт ложный хороший игровой рейтинг; отказ/удаление/новая сеть инвалидируют применение. Ручной режим сохраняется.

## 8. WN-05 — минимальная пауза

Сначала классифицировать тип изменения:

| Изменение | Политика |
|---|---|
| Небольшое улучшение при живом активном пути | Сохранить текущую сессию; улучшать после idle либо только безопасные новые flows |
| Ручной переход между допустимыми личными путями | Подготовка → проверка → подтверждённый apply. Старые потоки сохраняются только после классификации намерения как soft preference и подтверждения native capability. Обязательный новый выход/страна/идентичность — strict policy: прежний недопустимый путь прекращается для затронутого scope |
| Direct → защищённый, блокирование, отзыв ключей/пути | Явное ужесточение политики важнее drain; старый запрещённый трафик не оставлять жить ради «бесшовности» |
| Отказ сервера | Подготовленный разрешённый резерв; восстановить только затронутый scope, не перезапускать всю систему из-за одной карточки |
| Смена physical network | Использовать существующий monitor/native механизм; инвалидировать старые результаты и восстанавливать в bounded-порядке |
| Новый native outbound вне live capability | Не притворяться мгновенным; подготовить совместимый путь/worker, иначе сохранить текущую сеть и показать конкретное ограничение |

Flow pinning не исчерпывает задачу: игровая сессия может открывать несколько связанных TCP/UDP-соединений и ожидать один внешний IP. Для неизвестного поведения безопаснее удержание пути приложения до idle, чем автоматический перенос каждого нового flow на другую сеть. Отдельная fixture должна проверять дополнительный login/UDP канал.

**Приёмка:** неизменные TUN/PID/native session при подтверждённо совместимых live-изменениях, живые соседние потоки, отсутствие лишних resets, корректная очистка удержанных workers, OFF/revoke побеждают pending transition. Для несовместимого изменения Android native graph сохраняется существующее явное structural consent; CAP-04 не доказывает возможность его live-применения. Данные карты и карточки показывают реальное применение.

## 10. Измерять пользовательский эффект

Начальные числа ниже — **предлагаемые цели лабораторной приёмки**, не измеренные достижения и не SLA внешнего интернета. В WN-01 выбрать reference-машину/телефон, зафиксировать baseline и метод. Корректировка цели требует фактического измерения и записи причины.

| Метрика | Начальная цель/правило | Как измерять |
|---|---|---|
| Лишние TUN/native restarts от browsing/probe/совместимой правки | 0 | Runtime PID/session + журнал owner, не визуальный переключатель |
| Сбросы незатронутых соединений | 0 | Длительный контрольный поток и счётчик reconnects |
| Сбросы здорового active flow при soft improvement | 0 для подтверждённого capability | TCP/UDP fixture, обе стороны, правильный policy class |
| UI-ответ на выбор/отмену | p95 до 100 мс на reference | Input → видимое изменение, отдельно от завершения сети |
| Работа видимой карты | p95 frame до 33 мс при 10k/2k | Pan/zoom/selection на production renderer/Android, не headless снимок |
| Нагрузка скрытой карты | Нет собственного постоянного animation/probe loop | Lifecycle/CPU/job counters |
| Время готового резервного выбора | Цель до 1 с после подтверждённого отказа, если путь уже подготовлен | Отдельно от detection time и времени reconnect самого приложения |
| Пауза потока при мягкой правке | Стремиться к baseline + 50 мс в controlled fixture, без resets | Максимальный межпакетный gap и распределение, несколько прогонов |
| Память/пакет карты | Сначала измерить delta, назначить потолок до merge | Открыть/закрыть карту серией, сравнить baseline; не утверждать по размеру npm-пакета |
| Стоимость подробного теста | Ограничение времени/байтов до запуска | Реальные sent/received bytes, cancellation и отсутствие скрытых повторов |

Не объединять в одну цифру: локальное принятие решения, probe, native ACK, обнаружение отказа, handshake резерва, пауза пользовательского потока и повторная авторизация. «Несколько миллисекунд на таблицу» не доказывает «игра не заметила».

## 11. Среда UI/UX-приёмки

Windows: текущая минимальная поддерживаемая ширина и реальные 900/1240/1600 px, обычный и увеличенный DPI; длинные имена, пустой каталог, несколько страниц, 10k кандидатов. Сохранить существующий клавиатурный focus, Escape/Back и scale. Не объявлять 620 px обязательным новым размером окна, если текущий shell его не поддерживает; использовать его как стресс-layout fixture, когда это уже есть в тестах.

Android: 320–360 dp как стресс компактности и обычный reference-телефон; fontScale 1.0/1.3/2.0, IME открыта/закрыта, portrait/landscape, Back, TalkBack/семантика, уведомление во время нажатия. Существующая API/ABI/optimized-release матрица остаётся gate, когда меняется native/runtime.

## 12. Условия остановки отдельного изменения

- Потребовался второй TUN, замена движка или обход owner-контракта ради карты/проверки — остановить этот вариант и зафиксировать совместимый fallback.
- Для сохранения потока приходится продолжать отозванный/недопустимый путь — исправить классификацию, не снижать правило.
- Не подтверждено, по какому outbound прошла проверка — результат не участвует в рекомендации маршрута.
- Не удаётся уложить карту в устройство — сохранить список и ограничить детали; не заставлять весь продукт зависеть от GPU.
- Выявлено изменение соседнего кода — обновить локальную базу и конкретный integration diff, не перезаписывать файлы старой копией.
- Визуальная проверка не выполнена — статус NOT_RUN/BLOCKED; не повышать его до PASS по source tests.
