# 04. Пул корректировок: продолжить Waarp, не перестроить

**Статус всех новых задач: PROPOSED, не DONE.** Дата 17.11.2026. Основание — [исследование](README.md), существующий `TZ-NEXT`, его журнал приёмки и текущий код. Сначала сверить новый `main` с аудитным `866d037…`: Claude параллельно ведёт USB-отладку. Если функция уже принята в новом коде, подтвердить её и отметить ALREADY_DONE, а не реализовывать второй раз.

## 1. Очереди и границы

**Первый ограниченный проход:** N01 → N03 → N04. Это открытие уже существующей способности core, доступная offline-диагностика и исправление сдвигов от обратной связи. N01 не объявлять исправлением текущего AWG-сбоя.

**Следующий проход после стабилизации handset:** N02 → N05 → N06 → N07. N02 формирует корректное измерение; N05 — вертикальный MASQUE-путь; N06 — небольшой helper; N07 продолжает существующий Э7.

**По отдельному подтверждённому кейсу:** N08. **Проверка каждого прохода:** соответствующая часть N09, не только unit tests. **R&D без production-изменений:** N10.

Не выполнять все десять задач одним большим коммитом. Не менять engine pin только ради N01 без доказательства необходимости. Не изменять дизайн-систему, число разделов навигации, карточки, master intent, модель секретов или механизм live route apply.

## N01. Довести `chrome_155` через существующие мапперы

**Основание:** закреплённый core знает значение; Android и desktop allowlists его не принимают. VLESS default остаётся Firefox. [L04][L05][L06][P07][P08]

**Где:** Android `data/ProfileImporter.kt`; desktop `src/main/vless.ts`, `src/main/links.ts`; соответствующие существующие тесты импорта. Проверить также технический просмотр и сериализацию, не добавлять отдельный редактор.

**Сделать:** явный поддерживаемый вариант без изменения смысла старого `chrome` и без миграции сохранённых профилей. При необходимости маленький общий список capabilities в существующем слое, не новый registry framework.

**Готово, когда:** профиль с `fp=chrome_155` сохраняет значение после roundtrip и передаёт его в core; неизвестное значение отклоняется; Firefox-default и старые профили неизменны; pinned native config check выполнен отдельно для нужных платформ. Live TLS/REALITY с совместимым сервером — отдельный результат, а не вывод из parse PASS.

**Stop:** если конкретный распространяемый binary не поддерживает поле, не маскировать отказ и не менять всю поставку автоматически. Записать точную версию/ошибку и согласовать следующий шаг.

## N02. Проверять полезную передачу, не только URL latency

**Основание:** РФ/Cloudflare и Иран демонстрируют классы ограничений, при которых короткий обмен не показывает пригодность пути. [R01][I01] Детальный контракт — [03 §2](03-DIAGNOSTICS-AND-RECIPES.md#2-лестница-проверки-полезного-канала).

**Где:** существующие Android `data/HealthProbe.kt`, `NetworkTools.kt`, `core/HeadlessProbe.kt`, `LibboxBackend.kt`, `NativeLane.kt`; desktop существующий диагностический owner, обнаруженный исполнителем. Не создавать второй параллельный checker.

**Сделать:** добавить результаты download/upload с подтверждённым payload, direction, размером и deadline. Не мерить upload на чужом непредназначенном endpoint. Отсутствующая возможность = NOT_MEASURED. Предложенный быстрый budget 60s/2MiB — проверить и утвердить измерением.

**Готово, когда:** тесты воспроизводят tiny-ответ+обрыв после первых байтов; хороший download+сломанный upload; неверный payload/redirect; метered-сеть; отмену до/после открытия сокета; OFF и смену сети; отсутствие разрешённой цели. Неизмеренное не становится PASS. Применяется только результат текущего профиля/сети. Старый рабочий маршрут не переключается на основании одного шумного измерения.

**Не делать:** национальный whitelist classifier по порогу скорости, удаление «нулевых» профилей, бесконечный speedtest, новый backend телеметрии.

## N03. Сохранить последнюю неудачную сессию для offline-экспорта

**Основание:** пользователь не может передать текущие логи, пока не выйдет из Waarp и не включит другой VPN. Это реальный UX-сценарий, не требование присылать секретный config.

**Где:** существующие runtime log/status owner, репозиторий и Android экран диагностики/системный share. Уточнить актуальные точки хранения в новом main; не выводить native log в plaintext-файл без redaction.

**Сделать:** ограниченный локальный снимок стадий/ошибок/версий/результатов до очистки runtime. Состав общего отчёта — allowlist. Сохранение и экспорт не требуют подключения и не меняют route intent.

**Готово, когда:** вызвать неуспех → OFF → другой VPN → пересоздать Activity/процесс → открыть отчёт; данные сохранены и различимы по времени сессии. Fixtures с keys, subscription URLs, passwords, headers и произвольными native errors не раскрывают секреты. Работают ограничение размера, удаление, отказ записи и просмотр состава до передачи.

**Не делать:** сервер логов, автозагрузку отчёта, хранение полной конфигурации, обязательный аккаунт, новый раздел навигации.

## N04. Устранить сдвиги от обычного результата действия

**Основание по исходнику:** `OperationFeedback` условно вставляет `InlineMessage` внутрь `Panel`/Column. На Home блок стоит под переключателями режима. Это источник изменения высоты; точная величина на устройстве ещё не измерена. [L07][L08]

**Где:** `ui/UiComponents.kt`, его конкретные вызовы в `HomeRoutes.kt` и текущих формах. Для snackbar использовать существующий верхний host, если он уже есть; не строить новую систему уведомлений.

**Сделать:** обычный успех не вставляет новый блок в поток карточки. Подойдёт существующий snackbar либо компактный заранее стабильный статус. Блокирующая ошибка остаётся заметной и доступной; не обрезать текст ради геометрии. Не использовать одну анимацию высоты как «исправление»: элемент всё равно перемещается.

**Готово, когда:** при повторных одинаковых действиях и приходе success-статусов координаты соседней кнопки/переключателя не меняются; фокус и scroll position сохраняются; сообщение доступно TalkBack и не спамит. Отдельно проверить font scale, маленькую ширину, клавиатуру и error-состояние. Намеренное открытие пользователем подробностей допускает reflow; спонтанный success — нет.

**Жёсткий лимит смысла:** сохранить тему, размеры основных карточек, навигацию и существующие контролы. Допустима точечная уборка дублирующихся подписи/пояснения в этом же блоке. «Пустые настройки» не заполнять неработающими галочками.

## N05. MASQUE поверх существующего движка

**Основание:** core capability имеется, законченного app import нет. [P06][L04]

**Где:** существующий importer/model/compiler/technical view и текущая форма профиля; сначала Android, desktop отдельной приёмкой. Повторно проверить exact binary capabilities, а не только upstream docs.

**Сделать:** типизированный MASQUE-профиль с сохранением обязательных ключей и inner addresses, явным `vhttp` и валидацией применимости H2/H3/auto. Никаких общих credentials. Generic full-runtime JSON import в эту задачу не входит: нельзя принимать произвольный TUN, управляющий listener, файловые пути или исполняемые hooks.

**Готово, когда:** malformed/unsupported fields отказаны явно; roundtrip не теряет ключи и режим; неправильный ключ не даёт success; выполнена матрица [02 §3](02-PROTOCOLS.md#3-masque-полезный-дополнительный-путь-не-универсальное-лекарство) на контролируемом endpoint; Android OFF/cancel/revoke остаются корректными. H2 и H3 имеют отдельные результаты и одну обозначенную доверительную границу Cloudflare.

**Stop:** нет актуального корректного enrollment/export/endpoint — предоставить точный BLOCKED. Не обходить TLS, не подменять endpoint популярным доменом, не добавлять второй Xray core как незаявленную зависимость.

## N06. Малый helper совместимых вариантов

**Зависит:** N01/N02; MASQUE-варианты только после N05. Использовать существующие selection policy, memory и token freshness; не второй scheduler.

**Сделать:** доступное из текущей карточки действие «Подобрать рабочий вариант» с максимум несколькими допустимыми кандидатами, исходником и откатом. До теста показать, что меняется и нужен ли серверный counterpart. После теста — «проверен в этой сети, тогда-то», а не «обходит блокировки РФ».

**Готово, когда:** неподходящий рецепт не предлагается; исходник не меняется до подтверждения; stale result/смена сети/удаление профиля блокируют Apply; успешный текущий канал не раскачивается; rollback восстанавливает exact original; ошибка применения видна. Защищённый путь не превращается в Direct.

**Не делать:** десятки видимых параметров, случайные SNI/ключи/AWG headers, silent downgrade, автоматический experimental-пул.

## N07. Довести служебные загрузки через разрешённый путь

**Основание:** незакрытая часть существующего Э7, а не новая архитектура. [L02]

**Где:** текущий repository/subscription/catalog updater и его сеть. Сохранить один owner и отмену.

**Сделать:** явный выбор разрешённого личного пути для служебного HTTPS; последний проверенный локальный cache доступен offline. Требования сертификата/имени, размер, redirect policy, целостность и срок сохраняются. Не копировать trust-all из WL-fork. [P05]

**Готово, когда:** заблокированный bootstrap не уничтожает старую конфигурацию; отказ cache/write/cancel не публикует частичный результат; запрос действительно идёт указанным путём; нет скрытого Direct fallback или утечки URL подписки в общий отчёт; отозванный профиль не воскресает.

## N08. Разрыв Android/desktop по параметрам — по одному семейству

**Основание:** Android importer на срезе не принимает AWG3-поля и полную hopping-схему HY2. [L04][P11][P13]

**Порядок:** сначала выбрать конкретный предоставленный пользователем/server-side кейс; закончить его A→Z. Следующее семейство — отдельный проход. Не трактовать этот заголовок как приказ «поддержать все протоколы».

**Готово, когда:** exhaustive map нужных полей, отрицательные значения/диапазоны/unknown keys, roundtrip, exact core check и реальный interop; отличия от desktop явно документированы. Не изменён wire format уже рабочих AWG1/2. Неподдержанное не пропущено молча. Нужный сервер отсутствует — NOT_RUN для interop, не DONE всего семейства.

## N09. Полевая приёмка каждого изменённого пути

Это проверка достигнутого, не повод строить новую огромную тестовую платформу. Использовать существующие fixtures, Android acceptance и USB-стенд.

**Минимальная матрица:** исходный рабочий домашний путь как контроль; текущий мобильный оператор; ещё одна реально доступная независимая сеть; выбранное приложение и всё устройство; DNS+IP цели; upload/download; экран off; Wi-Fi↔mobile; пользовательский OFF; параллельный desktop только с отдельной peer identity; неверные credentials и недоступный endpoint.

Для каждой строки фиксировать device/API/ABI, client/core/server версии, network label, время, effective config hash без секрета, конкретный исход и retained evidence. Где нет среды — NOT_RUN. Эмуляторный локальный AWG сервер не подписывать «прошло на Билайне».

**Готово, когда:** новые случаи проверены, рабочий контроль не регрессировал, небольшие автоматические тесты воспроизводят исправленный класс, отказ не превращается в зелёный статус, файлы отчёта позволяют отличить network issue от core/lifecycle/route.

## N10. Исследовательская полка, не скрытая реализация

Кандидаты: NaiveProxy/Chromium networking, XDRIVE, QUICstep, CircumVolve, актуальные мосты Tor. [P12][P04][F01][F02][P16]

Для каждого достаточно карточки: threat model, зависимости, trust/license, доступный сервер, ограничения платформы, минимальный эксперимент, критерий успеха и цена сопровождения. Результат может быть «не брать сейчас».

Не исполнять сгенерированные модели код/скрипты на телефоне, не включать чужой beta-binary без supply-chain review, не добавлять публичную телеметрию без согласия. Новая внешняя лицензия/встроенный core — отдельное решение владельца.

## 2. Общая приёмка и отчёт исполнителя

На каждую выполненную задачу коротко:

`ID | DONE / ALREADY_DONE / BLOCKED | commit | изменённые точки | PASS/FAIL/NOT_RUN по проверкам | ограничения`.

Не ставить DONE из наличия кода. Раздельно указать: parser/JVM, pinned native config, controlled server interop, emulator, physical device/network. Не менять критерии постфактум ради зелёного CI. Версии и sha должны относиться к реально проверенному дереву.

Изменения docs этого исследовательского корпуса сами по себе не являются ни реализацией N01–N10, ни доказательством stable релиза.
