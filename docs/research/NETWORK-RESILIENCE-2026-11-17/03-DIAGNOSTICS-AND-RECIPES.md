# 03. Диагностика, безопасные рецепты и мобильный контур

Все численные бюджеты в этом файле — **предлагаемые стартовые ограничения**, а не измеренные пределы сети. Корректировать по retained evidence, не ослабляя требования отмены, приватности и честного результата. Реализовывать внутри существующих владельцев работ и памяти сети; не создавать параллельную систему Auto.

## 1. Что именно сломалось

| Наблюдение | Что допустимо заключить | Что проверять дальше |
|---|---|---|
| Нет физической сети/адреса | Транспорт сейчас недоступен | Состояние Android-сети, переход Wi-Fi/LTE, captive portal |
| VPN запущен, счётчик вырос | Локальный runtime работает и видел байты | Установление защищённого пути и подтверждённый ответ цели |
| TCP connect успешен, TLS нет | Доступен TCP к этой цели; TLS не завершился | Ошибка trust/time/SNI, сервер, сеть; не выводить DPI автоматически |
| Handshake успешен, небольшой ответ есть | Короткий обмен возможен | Payload существенно больше короткого ответа, upload, удержание |
| Скачивание работает, отправка почти нет | Асимметричная непригодность измеренного пути | Отдельный upload и повтор на независимой цели; MTU/потери/ограничение |
| UDP не ответил | Не получили ожидаемый ответ данного UDP-протокола | Контрольный разрешённый сервер; timeout не доказывает блок всего UDP |
| DNS-ответы различаются | Наблюдается различие | CDN/география/кэш, trust и HTTP-результат; не объявлять подмену |
| Один сайт не работает, другие работают | Частичный отказ | Правило, DNS, конкретная платформа, геоограничение, сервер назначения |
| Все проверенные внешние пути не работают | Не найден рабочий путь в данном наборе | Ограниченный/отключённый интернет возможен; причинность пока неизвестна |
| После смены сети ухудшилось | Изменился контекст | Устаревшие сокеты/резолвер/MTU/health, а не немедленно «забанили VPN» |

Такая осторожность не мешает автоматическому восстановлению: приложение может предложить альтернативный **проверенный** путь без выдуманного диагноза о виновнике. OONI отдельно предупреждает о неоднозначности аномалий и необходимости контекстной интерпретации. [G04]

## 2. Лестница проверки полезного канала

### A. Контекст и предварительные условия

Снимок содержит generation runtime, generation физической сети, hash эффективного профиля, тип интерфейса, metered/unmetered и время. Не использовать SSID/координаты/телефонный номер как обязательный идентификатор. ASN/оператор, если получены, остаются локальными и не заменяют реального теста.

Проверить VPN consent, конфликт другого VpnService, текущий route intent, default route, shared DNS, доступность записи конфигурации. Android platform lifecycle/protect уже существует — задача не переписывает его. Подписки и физическая диагностика не должны случайно уйти через проверяемый туннель, когда заявлены как Direct-контроль. [L03][P19][P20]

### B. Малый проверяемый обмен

Для кандидата выполнить разрешённый текущим runtime механизм проверки, подтвердить TLS/прикладной ответ и фактический outbound. Сохранять исходные scheme/host/port/path. Успех обращения не равен любому HTTP-коду: тип ожидаемого ответа определён тестом. Перенаправление, captive portal и блок-страница не считаются payload success.

### C. Полезная передача

Предложение для ручного быстрого теста: до трёх совместимых кандидатов; по одной проверке за раз, без второго WG-instance; минимум один payload **64 KiB download**, и при наличии подходящей контролируемой цели — **32 KiB upload** с подтверждением nonce/длины сервером. Объём выбран как инженерный старт, а не универсальный порог цензора.

Нельзя посылать тестовый POST на случайный сайт. Если нет разрешённого upload endpoint, результат upload = **NOT_MEASURED**, а не PASS. Использовать существующие контролируемые тестовые endpoints или явную настройку владельца; инфраструктура Waarp в этой работе не предполагается существующей.

Измерять time-to-first-byte, объём подтверждённых полезных байтов, длительность, timeout/error и направление. При достаточной телеметрии можно использовать пассивное качество реальных соединений без нового тестового трафика, но без чтения пользовательского содержимого.

Общий стартовый budget ручной проверки: максимум **60 секунд и 2 MiB** суммарно, включая повторы; UI до начала сообщает объём. При плохой сети не устраивать немедленную серию повторов. Дополнительный объём/длительный тест — отдельное явное действие.

### D. Устойчивость

Короткий тест означает «проверен сейчас», а не «стабилен». Для ручной расширенной проверки предложены 3–5 минут с ограниченным числом коротких обменов, idle/wake и двунаправленной передачей. Для инженерной приёмки — более длинный сценарий с server-side corroboration, сменой сети и экраном off. Не менять существующий обязательный release soak ради быстрого результата.

Проверку не надо превращать в непрерывный speedtest. На мобильной сети качество и успешное удержание важнее максимальных мегабит; постоянные тесты сами расходуют батарею и тариф.

### E. Применение

Успешный результат связан с контекстом A. Перед применением повторно проверить его актуальность. Смена сети, удаление/замена профиля, OFF и истечение срока делают результат неприменимым. Сохранённый выбор при новом контексте — **кандидат для перепроверки**, не вечная истина. Существующие cancellation/token/ownership механизмы сохранить. [L02]

## 3. Выбор: пригодность, потом устойчивость, потом скорость

Предлагаемая последовательность без непрозрачного магического score:

1. Есть доступный совместимый endpoint и действующие credentials.
2. Прошла обязательная для задачи проверка подлинности и полезной передачи.
3. Нет подтверждённого провала нужного направления; отсутствие измерения показано отдельно.
4. Текущий здоровый путь удерживается, особенно при активных соединениях.
5. Среди действительно пригодных вариантов учитываются устойчивость, задержка, затем скорость и стоимость трафика.

Не менять путь из-за одного медленного запроса. Не копировать из чужого клиента численные границы «18 KB/s = whitelist». Маленькая скорость может быть следствием перегрузки, тарифа, сервера или тестовой цели. Результат формулируется как «этот путь передаёт данные слишком медленно для выбранной задачи».

Профиль с нулевым результатом не удаляется. Временная недоступность не портит исходные credentials и не выключает защищённый маршрут. Автоматический Direct fallback запрещён без отдельного решения пользователя.

## 4. Рецепт — ограниченный вариант, а не случайный набор полей

Рецепт описывает: ID/версию, требуемые возможности exact core, применимые протоколы, поля изменения, условия сервера, причину попробовать, ограниченный тест, результат, срок перепроверки и способ отката. Сами ключи остаются в существующем защищённом профиле. `recipes.example.json` — образец метаданных для обсуждения; новая DSL/фреймворк не требуется.

| Рецепт | Допустимое изменение | Обязательное условие / предел |
|---|---|---|
| Исходный рабочий | Ничего | Первый кандидат и точка отката |
| Современный TLS fingerprint | Явный `chrome_155` | Поддерживается фактическим core и серверной комбинацией; TLS trust сохраняется |
| MASQUE H3 | Выбор H3 в импортированном MASQUE-профиле | Доступен QUIC/UDP endpoint, корректные ключи; сайт Cloudflare не заменяет тест |
| MASQUE H2 | Выбор H2 в совместимом профиле | Реализация/server действительно поддерживают H2; не добавлять это стандартному профилю молча |
| Экономный мобильный | Только проверенные локальные параметры / частота probes | Не изменяет формат, который ожидает сервер; не жертвует контролем здоровья |
| Запасной доверенный вход | Выбор заранее добавленного пользователя endpoint | Не поиск чужих relay, не подстановка популярного SNI к случайному IP |

Экспериментальный XDRIVE, неподтверждённый Naive или новая hopping-схема не участвуют в обычном авто-подборе, пока не принят отдельный vertical slice.

## 5. Какие крутилки полезны

**Базовый слой:** путь, режим маршрутизации, «Проверить», «Подобрать рабочий вариант», «Вернуть исходное». Существующие экраны и карточки остаются.

**Расширенный слой конкретного профиля:** только поля, которые реально применимы и валидируются. Для каждого — понятное назначение, текущее/исходное значение, условие совместимости и отметка «потребует переподключения». Временный тестовый overlay не переписывает импортированный исходник до подтверждения.

**Серверно-согласованные параметры:** ключи, Reality public key/short ID, транспортный путь, пароль Salamander, AWG-параметры формата и серверные ограничения не крутятся поиском. UI показывает «изменяется вместе с сервером», а не кнопку randomize. Формат AWG и дополнительные поля описаны первичным проектом. [P11]

**Локальные параметры, которые всё равно требуют проверки:** fingerprint, разрешённые данным core методы разбиения ClientHello, MTU вниз от согласованного исходника, допустимые интервалы и выбор H2/H3. Не все они применимы каждому протоколу. Не выдавать desktop packet injection или Linux/root-функции за возможности Android без root. [P14][P19]

**Никогда автоматически:** trust-all, `allowInsecure`, отключение проверки имени/ключа, неизвестная цепочка relay, глобальное выключение IPv6, изменение credentials, изменение цели пользователя, загрузка исполняемого кода из рецепта.

## 6. Мобильные нюансы, которые легко принять за блокировку

**Физическая сеть и VPN-сеть — разные сущности.** Внешний сокет должен выходить по правильному защищённому от рекурсии пути. События Android callbacks и ownership уже имеют своих владельцев; проверять реальное поведение при Wi-Fi→LTE и обратно, а не вводить новое глобальное bindProcessToNetwork. [P19][P20]

**IPv6 снаружи и внутри туннеля независимы.** Проверять отдельно доступность IPv6 endpoint, внутренний IPv6, DNS/AAAA и поведение IPv4-only профиля. Для IPv6-only/NAT64 сети literal IPv4 endpoint — отдельный обязательный тест. Нельзя объявлять любой IPv6 источником проблемы и выключать его во всём устройстве. Контракты трансляции отличаются от доступности конкретного сервера. [P24]

**MTU и небольшие успешные пакеты.** В успешном handshake ещё нет проверки больших пакетов. Длинный HTTP/TLS обмен, upload и размеры datagram должны входить в тест. Пробовать только контролируемый диапазон, показывая исходное и эффективное значение. Нельзя лечить неверные S/H AWG-поля MTU-перебором. [P11]

**Сон, NAT и таймеры.** Проверять экран off, Doze, возврат из idle, смену внешнего адреса и восстановление текущего профиля. Пользовательский OFF не должен отменяться recovery. Изменение keepalive — осмысленная цена батареи, не бесплатное ускорение.

**Один WireGuard peer на двух устройствах.** WireGuard обновляет endpoint по аутентифицированному источнику. Поэтому одновременное использование одной peer identity на ПК и телефоне может мешать чистому сравнению. Проверить отдельными клиентскими ключами/peer или последовательным запуском. Это диагностическая гипотеза, **не установленная причина пользовательского обрыва**. [P22]

**DNS Android без атрибуции приложения.** Не подменять владельца DNS фиктивным Telegram UID. Существующий общий DNS intent должен следовать явной политике и не уходить в Direct при защищённом намерении. Смена сервера DNS не чинит недоступный транспортный endpoint. [L03]

**Другой VPN на телефоне.** Revocation/остановка Waarp при запуске другого VPN — отдельное состояние, не доказательство падения AWG. Диагностический отчёт должен оставаться доступным после этой смены.

## 7. Offline-инцидент: чтобы пользователь не добывал логи без интернета

Предложение: сохранять ограниченный локальный пакет последней неудачной сессии **до** очистки runtime. Включить времена этапов, версии, generation, количество/тип ошибок, применённый рецепт без секретов, состояние маршрута, физической сети и результат отдельных проверок. Разделять «не было данных» и «данные были, но экспорт не удался».

Не сохранять необработанный native log без фильтра: исключить keys/passwords/tokens, URL подписок, полный config, пользовательские адреса посещения и имена приложений из общего отчёта. Нужные для ручной глубокой отладки дополнительные сведения — отдельное явное согласие, локально. Перед передачей пользователь видит состав.

Работает без интернета, после OFF, после запуска другого VPN, после пересоздания Activity. Экспорт через системное «Поделиться» не должен запускать сеть. Ограничение объёма/числа записей, защищённое локальное хранение и удаление — обязательны. Не создавать backend телеметрии по умолчанию.

## 8. Будущее: сценарии, а не обещания

| Сценарий | Ранний наблюдаемый сигнал | Готовность Waarp |
|---|---|---|
| Блокируют известные IP/ASN | Несколько транспортов на одном входе не работают, независимый вход работает | Независимые доверенные endpoints, не только вариации одного SNI |
| Ограничивают UDP/QUIC | Воспроизводимый провал конкретных UDP-путей при рабочем контроле TCP | Совместимый TCP-путь; H2 там, где реально поддерживается |
| Пропускают начало, режут данные | Handshake/малый ответ успешны, payload/удержание нет | Проверка полезного объёма и двух направлений |
| Меняется TLS fingerprint detection | A/B одного серверного пути даёт различие на версии клиента | Версионированный небольшой набор, rollback, без глобальной миграции |
| Доступ только к ограниченному набору сервисов | Многократные разнотипные проверки показывают частичную связность | Честный статус и заранее доступный авторизованный вход; не обещать SNI-магию |
| Блокируют bootstrap/обновления | VPN-профиль есть, служебные HTTPS недоступны | Offline cache + явный разрешённый личный путь загрузки, подписи и freshness |
| Доступ исчезает физически | Нет работающего внешнего пути, сеть/инфраструктура недоступны | Bounded retry, сохранение состояния, объяснение предела клиента |
| Детектируют более сложное поведение | Пресет TLS перестал быть достаточен | Отдельный R&D: Chromium stack, cloud transports, QUIC migration, проверяемые стратегии |

Последняя строка включает NaiveProxy, XDRIVE, QUICstep и CircumVolve. У каждого свои допущения и стоимость. Нельзя автоматически превращать опубликованный эксперимент в production-рецепт. [P12][P04][F01][F02]

## 9. Обновляемый корпус без скрытой удалённой власти

Сейчас достаточно версионированных документов и небольшого встроенного списка рецептов. В перспективе пакет данных может иметь schema version, ограниченный набор ключей, подпись, срок актуальности, minimum core и rollback. Истёкшее знание не удаляет личные профили. Компрометация источника не даёт произвольно изменить туннели, запустить код или снять TLS-проверку.

Предлагаемая частота ручной ревизии: критические мобильные случаи — по новым воспроизводимым сбоям; release notes — при плановом обновлении движка; страновые карточки — регулярно и после крупных событий. Это рекомендации процесса, не созданный фоновый мониторинг.
