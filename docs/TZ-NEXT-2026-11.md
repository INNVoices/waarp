# Waarp: аудит, решения, исследование и ТЗ (ноябрь 2026)

Обсуждение 17.11.2026 и уточнённое задание после аудита кода. **Цель: довести существующий стабильный маршрутизатор небольшими изменениями, сохранить карточки и живое применение маршрутов.**

**Актуализация 18.11.2026:** обе платформы находятся в `main`; владелец разрешил прямое обновление этой ветки. Текущие изменения и отдельные уровни приёмки описаны в [аудите маршрутов и подключений](ROUTE-AND-CONNECTION-AUDIT-2026-11-18.md). Ниже сохранено основание первоначального ТЗ. Исторические ссылки на ветки, количество предзагруженных профилей и перезапуск после неудачного ACK не являются указанием вернуть старое поведение.

**Срез аудита:** `feat/live-route-slots`, `4e0a2efcc7136eb572d3cf7a25a8b719bc0283b8`; `main` на момент проверки — `6ffde69`. Закреплённый движок — `sing-box-lx 1.14.2-lx.11`, а не последняя версия upstream. Разделы 1–8 объясняют решения; исполняемый объём, порядок и приёмка находятся в §9. Историческая проблема не становится новой задачей, если уже исправлена.

Исходная запись разговора и подборка стран сохранены в [версии до аудита](https://github.com/INNVoices/waarp/blob/4e0a2efcc7136eb572d3cf7a25a8b719bc0283b8/docs/TZ-NEXT-2026-11.md). В этой редакции исправлены недоказанные диагнозы, сведения об импорте и чрезмерный обязательный объём; принятые направления развития сохранены.

## 1. Что это за продукт

- Открытая оболочка-маршрутизатор трафика для Windows и Android в одном `main`. Похожа на ExitLag по концепции и интерфейсу: карточки «приложение / сайт → путь».
- **Своих серверов нет и не будет.** Всё автономно: подключения пользователя, общедоступные хосты, обход без сервера.
- Делаем в первую очередь для себя (ПК + Android). Если покроет большой кусок обходов и фишек — станет популярным сарафаном.
- Это **общий маршрутизатор**: приложения и сайты, игры, публичный Wi-Fi, гео-доступ и работа в ограниченных сетях. Улучшение пинга зависит от конкретного пути; multipath и гарантированное снижение задержки не заявляются.
- Не «чисто юзерфрендли»: техническая информация нужна всем, её не прячем (см. п. 7).

## 3. Что уже сделано в коде

Первоначальные изменения опубликованы в `feat/live-route-slots` (`4e0a2ef`) и позднее вошли в `main`. Раздел описывает тот этап; актуальное поведение дополняет отчёт от 18.11.2026. Повторная реализация уже действующей функции не требуется.

### 3.1 Карточки без перезапуска (слоты)

- Каждая карточка получает слот: файлы правил (local rule-set) + свой переключатель туннеля. Ядро само перечитывает файлы.
- Вживую: включение, выключение, создание, удаление, правка, смена туннеля, «Напрямую», перестановка.
- Применение проверяется локальным ACK каждого изменённого физического файла. Ошибка ACK требует отката с сохранением TUN; автоматический перезапуск в этой ветке ошибки запрещён. Один отдельный canary-файл не доказывает применение остальных правил.
- После правки закрываются соединения только затронутой карточки, приложение переподключается по новому пути.
- Безопасный ограниченный набор личных туннелей загружается заранее; фактические лимиты учитывают платформу, endpoint и watchers. Уже загруженные определения удерживаются до OFF.
- Рестарт требуется при действительно новом нативном определении, изменении credentials/транспорта или превышении бюджета. Общий путь, DNS, IPv6, LAN/RU и обычная правка карточек входят в живую политику в пределах поддерживаемого плана.
- Убрана лишняя проверка адаптера при рестарте (~2 с).

**По локальному отчёту Опуса проверено вживую:** 4 правки подряд — `live route apply ... core and TUN kept`, адаптер не отключался. Это подтверждение конкретной сессии, а не проверка всех операций/отказов Э0.

### 3.2 Остальное

- **Лог на диск:** `%APPDATA%\Waarp\logs\waarp.log`, 5 × 4 МБ с ротацией. Фазы, ошибки, время старта, применение карточек и причины рестартов, предупреждения ядра. Уровень ядра `warn`, подробный — `WAARP_ENGINE_LOG=info`.
- **DNS карточек приложений** — добавлены правила по процессу для запросов, чей процесс определён ядром. Для общего системного DNS Client принадлежность запросов отдельным приложениям требует проверки; обещание «любой DNS любого приложения всегда через его карточку» из этого изменения не следует.
- **IPv6:** если у системы нет IPv6, такие соединения «напрямую» сразу отклоняются.
- **ExitLag и другие VPN-клиенты** (WireGuard, Amnezia, OpenVPN, WARP, Hiddify, v2rayN и т.д.) направляются в outbound `direct`; своя карточка главнее. Это устраняет повторный удалённый туннель для совпавшего процесса, но не исключает его пакеты из обработки TUN и не доказывает устранение всей нагрузки.
- **Карточки Store** совпадают по пакету без версии, дубли сливаются. «Вся папка» у Store-приложения включает и его папку в `AppData\Local\<Издатель>\<Приложение>` (так покрывается `codex.exe`).
- **Интерфейс** показывает карточку по фактическому срабатыванию в ядре.
- **Движок portable** копируется в `%LOCALAPPDATA%\Waarp\engine\<хэш>\` с проверкой контрольных сумм.

### 3.3 Старт с первого раза (собрано в код, вживую не проверено)

- Проблема: первый старт после закрытия старой версии висел ~15 с и падал (`create adapter: ... already exists | open existing adapter: Element not found`), второй проходил.
- Причина: Waarp останавливает ядро жёстко (мягкий сигнал не отправить — у процесса нет консоли), Windows оставляет полуудалённый адаптер. Идентификатор адаптера постоянный: md5(`wintun` + `Waarp`) = `{78F04A7F-86C1-9212-9675-52E8987AC741}`.
- Реализация: перед стартом проверяется фиксированный instance ID `SWD\WINTUN\{78F04A7F-…}` и отсутствие адаптера Waarp, затем может вызываться `pnputil /remove-device`. Это изменение прежнего read-only recovery-контракта: отсутствие процесса-владельца и достоверность PnP-проверки должны быть доказаны; ошибка инспекции не равна отсутствию устройства. Ограниченный повтор запуска проверяется вместе с отменой и отсутствием второго core (Э0).

**Ограничение перед слиянием после этого аудита:** автоматическое подключение `clearTunGhost` в `index.ts` отключено. В `4e0a2ef` ошибки `Get-PnpDevice -ErrorAction SilentlyContinue` могли выглядеть как отсутствие устройства, `unknown/left` не запрещали start, а отмена `untilCancelled` не ждала завершения удаляющего helper. Разрушающий путь не включать обратно до Э0.3; обычный read-only preflight сохранён. Это не воспроизведённое повреждение сети, а установленный пробел нового механизма. Проверка slot-конфига добавлена в CI после `engine:fetch`, чтобы бинарный подпункт не пропускался из-за порядка шагов.

### 3.4 Проверки и границы доказательств

- В исходном локальном отчёте: 35/35 наборов, 49 проверок слотов с Windows `sing-box check` и проверки идентификатора адаптера.
- Независимый повтор на `4e0a2ef`, Linux / Node `24.22.1`: `npm run typecheck`, `npm run check`, `npm test` (35/35 без ошибок), `npm run build` — PASS. Четыре набора явно пропускают Windows/native IPC части; у слотов выполнено **48** проверок. Проверка Windows EXE условная и здесь не выполнялась.
- `npm run test:performance` — PASS: 1000 профилей / 201 маршрут, p95 **3.38 мс**, max **3.58 мс**, 17 загруженных endpoints. Это синтетическая компиляция конфига; измерение не покрывает runtime-слоты, Electron IPC, TUN, скорость сети или новый синхронный файловый лог.
- Windows TUN/UAC/ghost recovery и собственная десятичасовая сессия в этом аудите — **NOT_RUN**. Длительную стабильную работу пользователя принимаем как наблюдение; новые изменения проверяем адресно по [существующим условиям выпуска](STABLE-AUDIT-2026-11-16.md).
- Высокая загрузка четырёх процессов IDA в исходном отчёте — возможное объяснение фризов. Без совпадающего по времени профиля не приписывать все фризы ни VPN, ни IDA.

## 4. Обстановка по странам: справочный контекст

Исходная подборка по России, Ирану, Китаю и другим странам сохранена в истории документа и ссылках §10. Она смешивает первичные наблюдения, вендорские заявления, форумы и прогнозы. Это не основание объявлять протокол «мёртвым», выбирать настройку по стране или обещать обход в любой сети.

Для разработки полезны конкретные сценарии: сбой DNS, отказ TCP/TLS/UDP, ограничение отдельного endpoint, недоступность источника списков, отсутствие внешнего маршрута. Результат измерения содержит дату, сеть/оператора (если известны), цель, путь и версию профиля. Проверка из другой сети не заменяет локальную.

- Разные DNS-ответы допустимы у CDN и географической балансировки. Таймаут бывает из-за потери сети, сервера, маршрута или фильтрации. Методика [OONI](https://ooni.org/support/interpreting-ooni-data/) прямо требует учитывать ложные срабатывания.
- Числа из отдельных сообщений — «3 рукопожатия за 60 с», «130 с ожидания» и сроки жизни IP — не становятся универсальными константами Waarp. Ограничение нагрузки задаётся для собственного пробника и проверяется измерением.
- Правовые, бюджетные и политические прогнозы исключены из исполняемых требований. Нужные для отдельной публикации утверждения перепроверяются по первоисточникам на дату публикации.
- Работающий у пользователя WireGuard, Shadowsocks или OpenVPN сохраняется независимо от оценок в обзорах. Провал всех проверенных путей означает «доступный путь не найден», а не доказанный белый список или отключение страны.

## 5. Протоколы

### Решения и фактическая поддержка

Свои протоколы и второй движок не создаём. Используем возможности закреплённого sing-box-lx и существующие импортеры; каждое расширение решает конкретную совместимость. Различаем **поле в исходниках движка → импорт Waarp → принятие конфигурации бинарником → живое соединение**. Первый пункт не доказывает остальные.

| Протокол / возможность | Закреплённый движок и Waarp на срезе аудита | Решение |
|---|---|---|
| VLESS / REALITY / TCP / Vision / XHTTP | Импорт есть, `encryption` передаётся. **`pqv` находится в `notApplied`**, а не в рабочем outbound (`vless.ts:138`). XHTTP поддерживается в пределах явного mapper | Сохранить; исправлять доказанные несовместимости |
| AmneziaWG 3.1 | В pinned fork есть AWG 3.x поля, включая `header_protection_key`; модель/импорт Waarp пока покрывают старый набор | Небольшое расширение Э4 с корректным 3.1-профилем; старые профили не конвертировать автоматически |
| Hysteria2 / Salamander / port hopping | Salamander уже импортируется. В движке есть `server_ports` и интервалы, в Waarp — одиночный порт | Добавить hopping по официальному URI/профилю; сервер должен принимать заданные порты |
| NaiveProxy, AnyTLS | Есть в pinned исходниках/регистрации, импорта Waarp нет; build/interop отдельно проверить | Следующие небольшие расширения по одному, при наличии рабочего профиля |
| MASQUE / WARP | MASQUE есть в pinned исходниках; для WARP нужны регистрационные данные сервиса | Отдельная интеграция, не обещание готового бесплатного пути из одного импорта |
| TrustTunnel | В просмотренном pinned дереве/registry поддержка не найдена | Сохранить как идею; не включать в реализацию без конкретного совместимого backend |
| TUIC v5, Trojan, VMess, Shadowsocks, OpenVPN, AWG/WG | Импортеры уже есть | Сохранить рабочую совместимость, не удалять по географическому обзору |
| ShadowTLS, Mieru, Juicity, Tor WebTunnel | Не входят в текущий объём | Ранее принятое «позже / не берём» сохраняется |

**REALITY и ML-KEM.** Pinned `reality_client.go` уже сохраняет гибридную key share выбранного fingerprint, это покрыто upstream-тестами. `key_share: "hybrid"` проверяет её наличие и может отклонить несовместимый fingerprint; это не универсальный переключатель добавления ML-KEM. Проверить реальное подключение до изменения defaults. TLS key share, VLESS `encryption` и `pqv` — разные параметры. Массовое изменение работающих профилей не требуется.

**XHTTP.** Не вычищать `scMaxEachPostBytes` / `scMinPostsIntervalMs` по одному сообщению о детекте. Сохранить совместимые явно заданные значения; неподдерживаемые показать в `notApplied` с причиной. Обязательные параметры аутентификации/проверки сертификата нельзя молча отбрасывать ради успешного импорта.

### Границы кнопки «Подобрать»

| Параметры | Что допустимо |
|---|---|
| Fingerprint, ALPN, версия TLS, режим XHTTP | Небольшой набор совместимых с транспортом и сервером вариантов. Сохранить исходный профиль; не понижать проверку TLS |
| REALITY `serverNames`, `shortId`, SNI | Только исходные или явно предоставленные владельцем сервера значения. Произвольный другой SNI не является корректной контрольной проверкой |
| AWG junk / таймеры / MTU | Только документированные клиентские настройки. Согласованные S/H-поля, ключи и `header_protection_key` не угадывать и не менять независимо от сервера |
| Hysteria2 hopping | Только заданный провайдером список/диапазон доступных портов; не спасает от недоступности всего UDP |
| Профиль за CDN | Только совместимый endpoint и корректные Host/SNI/сертификат; массовый поиск чужих адресов не входит в задачу |
| Общий MTU TUN, DNS ОС | Не менять как скрытый побочный эффект подбора одного профиля: затрагиваются другие карточки |

Э3 начинает с известных путей и ограниченного ручного подбора; результат привязан к сети и версии профиля. «Не получилось подобрать» не означает доказанный блок IP.

## 6. Идеи и решения по ним

Согласованные направления остаются в плане. Их наличие здесь не означает обязательство реализовать всю инфраструктуру за один проход.

| Идея | Ближайший полезный объём | Дальше |
|---|---|---|
| Диагностика | Доработать существующий послойный пробник и применение проверенного пути (Э1) | Новые способы сравнения при наличии достоверного сигнала |
| «Напрямую + обход DPI» | Проверить поддержку и ограниченный режим одной карточки (Э2) | Расширять только после измерения совместимости |
| Подбор | Известные пути, небольшое число совместимых вариантов, отмена и откат (Э3) | Дополнительные параметры по реальным случаям |
| Протоколы | Корректность текущего импорта, AWG 3.1 / HY2 hopping при наличии тестового профиля (Э4) | Naive / AnyTLS; отдельная оценка WARP / TrustTunnel |
| Списки | Использовать существующие источники/кэш, добавить управление и безопасное обновление (Э6) | Общий `waarp-lists` и курирование сообществом |
| Служебная связь | Работа из кэша и понятный отказ обновления (Э7) | Подписанные зеркала, аварийный набор, updater |
| Публичные хосты | Источник, возраст и локальный результат проверки (Э8) | Добровольные публикации/измерения, верификация владения |

### 6.1 Общая проверка без новой подсистемы

Уже существуют `layered.ts`, `evidence.ts`, `Checker`, `Engine.probePaths`, Auto/группы и память сети. Расширять эти механизмы; общий формат результата и небольшие помощники вводить по реальной повторяемости. Проверка при включённом Waarp использует работающий движок; отдельный Checker без TUN — предусмотренный сценарий при выключенном Waarp. Не запускать второй экземпляр тех же AWG-учётных данных рядом с активным туннелем.

У задания есть общий deadline, ограниченная конкуренция, отмена и запрет публикации устаревшего результата после смены сети/профиля/выключения. Диагностика сама не изменяет маршрут; применение — отдельное явное действие, кроме уже включённой пользователем политики Auto.

### 6.2 Списки без хардкода

Использовать существующие `catalog.ts`, `SOURCES.md`, пресеты и механизмы кэша. Поддержать небольшой список источников с типом данных, URL, временем обновления и последним валидным результатом. Источники узлов и списки доменов — разные данные; скачивание списка не создаёт маршрут само по себе.

Первый проход — текущие форматы плюс простой список доменов, валидация размера/схемы/опасных широких шаблонов, сохранение последнего валидного снимка. Не нужен сразу универсальный конвертер geosite/всех чужих форматов. Ошибка загрузки/разбора не очищает рабочие правила. Изменение активного списка проходит тот же apply с подтверждением, что и карточка.

Автопредложение «добавить в карточку?» и отдельный репозиторий `waarp-lists` остаются следующими шагами. Единичный таймаут не создаёт постоянное правило. Пользовательские записи и выключенные источники сохраняются при обновлении.

### 6.3 Общедоступные хосты и сообщество

Разделять **доступность**, **проверку конкретных свойств** и **доверие оператору**. Исправный TLS, совпавший хэш файла, DNS-ответ или страна выхода не доказывают отсутствие журналирования/выборочной подмены. Метка «проверено» всегда называет проверку и её время; метки «честный/безопасный хост» нет.

- TXT-запись, подпись коммита или файл подтверждают контроль соответствующего домена/ключа/ресурса, но не честность и не обязательно личность оператора. Не вводить PKI сообщества в первый проход.
- Не сравнивать leaf-сертификаты обычных сайтов как неизменный эталон: CDN и ротация сертификатов допустимы. Использовать штатную проверку TLS; неизменяемый тестовый объект — только с известным содержимым и описанным назначением.
- Сохраняются явное добавление публичного узла и ограничения защищённых companion-карточек. Не подмешивать публичные узлы в личный Auto/fallback и служебную связь молча. Не угадывать «чувствительность» любого приложения по имени.
- GitHub Actions может публиковать доступность из своей сети, но не доказательство честности и не рейтинг проходимости из сети пользователя. Отправка результатов через issue/PR — отдельное добровольное действие.

### 6.4 Самозащита приложения

Начать с существующих кэшей и описи служебных зависимостей: источники каталога, списки, адреса проверок, DNS, будущие обновления. Сохранённые настройки и маршруты загружаются без ожидания внешней сети; видны возраст данных и результат обновления.

Подписи Ed25519/minisign, зеркала, ротация ключей, офлайн-набор и автоматический updater остаются отдельным следующим расширением Э7. Не подписывать чужие списки «за автора»: подпись подтверждает издателя/целостность, не правильность данных и не честность узлов. Контрольная сумма без доверенного источника не является подписью. Срок годности данных не должен мешать запуску приложения из последнего рабочего состояния; новые данные проверяются до замены.

Автоматическая лестница через публичные хосты, DNS TXT-маяк, IPFS и все перечисленные CDN одновременно не нужны для первого результата. Сначала понятный offline/cache-сценарий и разрешённый пользователем собственный путь. Секретные URL подписок и учётные данные не отправлять на новый публичный путь без явного выбора.

## 7. Видимость и режим разработчика

- Обычный режим: протокол, состояние, измеренная задержка и время проверки; страна с указанием происхождения (сейчас каталог извлекает её из имени, это не измеренный GeoIP). В «Подробно» — доступные адрес/порт/транспорт/SNI/fingerprint/MTU, выбранный путь и сработавшее правило. Не прятать обычную техническую информацию за dev-mode.
- Режим разработчика: дополнительные **read-only** представления конфигурации, маршрута и ограниченного лога, версия engine и экспорт диагностики. Использовать существующие страницы/панели; отдельный центр управления и редактор сырого JSON в этот проход не входят.
- Диагностический экспорт скрывает ключи, пароли, controller secret и секретные URL. «Скопировать подключение» — отдельное явное действие, предупреждающее о наличии секрета; его результат нельзя перепутать с обезличенным отчётом.
- Лог `warn` и ограниченная ротация сохраняются; подробный `info` включается для конкретной диагностики. Возраст/объём лога и имя текущего режима понятны пользователю.

## 9. ТЗ: этапы

### Главная цель и исполнение

Пользователь выбирает нужное приложение/сайт и путь. Waarp сохраняет стабильную маршрутизацию, показывает наблюдаемую причину отказа и предлагает проверенный доступный путь. Уточняем существующую реализацию; новый интерфейс, новое ядро и глобальная реорганизация модулей не требуются.

**Первый законченный проход: Э0 → Э1 → Э5.** Э2–Э4 и Э6–Э8 сохраняются как следующие ограниченные этапы, а не условия готовности каждого небольшого исправления. Каждый из них можно выполнить отдельно после указанных зависимостей; большие отложенные части из §6 не входят автоматически.

Для Opus medium:

1. Прочитать этот раздел и `CONTRIBUTING.md`. Начать с указанных для этапа исходников; читать непосредственные зависимости и тесты по необходимости, не расширяя аудит на несвязанные подсистемы. Проверить `git status`, актуальную ветку/HEAD и локальные изменения; выполненный пункт отметить `ALREADY_DONE` со ссылкой на код/проверку.
2. У каждого пункта есть основание, изменение и наблюдаемая приёмка. Исправлять существующего владельца функции; не создавать параллельный framework, второй store или ещё один пробник.
3. Сохранить главный переключатель, карточки, слоты, секреты, личные профили и предусмотренные случаи контролируемого рестарта. Блокировка новой функции не блокирует независимые исправления текущего прохода.
4. Проверять после связного изменения; исправить обнаруженную регрессию. Полный аудит всех подсистем и полный набор тестов после каждой строки не нужны.
5. В конце этапа: выполненные ID, изменённые файлы, фактические команды/результаты, ограничения. Статусы: `DONE`, `ALREADY_DONE`, `BLOCKED` (конкретно чего не хватает); у проверок — `PASS`, `FAIL`, `NOT_RUN`. Не считать эмуляцию проверкой Windows/TUN/реального сервера.

Это рабочий Markdown-шаблон по рекомендациям Anthropic о явном объёме и проверяемом результате (§10), не специальный официальный формат ТЗ. Effort выбирается в среде: `claude --model opus --effort medium` или `/effort medium`; в Messages API — `output_config.effort: "medium"`. Записать фактическую модель/версию: слово «medium» в документе настройку не меняет. XML-обёртка и новый `CLAUDE.md` для этого задания не нужны.

### Э0. Сохранить текущую стабильность и закрыть небольшие дефекты

**Основание:** слоты уже реализованы; полный код содержит точки, которые прежние тесты не покрывают. Сначала закрыть приёмку текущего поведения, не переносить её под разработку новых протоколов.

**Где:** `engine.ts` (`liveApply`, `writeRules`, `closeTouched`, `poll`), `tun.ts`, `logfile.ts`, `App.tsx`, `test/slots.check.ts`, `test/ui.browser.mjs`, `.github/workflows/ci.yml`.

**Уточнение Э0.2 от 18.11:** тот же контракт применяется к Android `MobileRepository`/`MobileLiveRouting`/`VpnController`. Проверять Direct → личный путь → другой путь, удаление последнего/неактивного маршрута, метаданные и ошибку каждой стадии применения. Неудачный live apply не превращается в stop/restart; откат либо подтверждён, либо затронутый набор заблокирован при сохранённом TUN. Пользовательский OFF остаётся отдельным намерением. UI показывает подтверждённое runtime-состояние, а не выдаёт сохранённый, но неприменённый выбор за работающий.

- **Э0.1 — история замеров.** `App.tsx:86–98` сравнивает `pings` по ссылке, а каждый IPC status создаёт новый объект; status трафика приходит раз в секунду, замеры — раз в 15 с (`engine.ts:301–334,628–648`). Добавлять историю по идентификатору/времени **нового измерения**, не по объекту status и не по изменению численного ping. Один sample + 20 клонированных status даёт одну точку; следующий sample с тем же ping — вторую. Старый результат удалённого профиля не возвращается; существующий лимит истории сохраняется.
- **Э0.2 — приёмка слотов.** Выполнить 10 изменений: on/off, создание/удаление, адрес/приложение, путь/Direct, порядок перекрывающихся правил. На поддерживаемом live-сценарии сохраняются PID core и идентичность TUN, меняется фактический маршрут новой сессии, соседняя длительная TCP/UDP-сессия сохраняется. Перестановку проверять с уже открытым соединением: текущий `closeTouched` не сравнивает порядок. Проверить отказ DELETE: `drop` пока не проверяет HTTP-статус, а лог считает выбранные ID как закрытые соединения. Считать подтверждённые закрытия либо честно показывать число попыток. Смоделировать отказ записи/задержку чтения одного файла при успешной канарейке; нельзя объявить весь apply успешным лишь по отдельному canary-файлу. При обнаруженном несоответствии исправить существующий apply, не заменять архитектуру.
- **Э0.3 — первый старт и проверка бинарника.** На одноразовой Windows проверить обычный/аварийный выход, ghost PnP, отказ инспекции/удаления, отмену запуска и соседний VPN. Только подтверждённый собственный остаток и отсутствие живого владельца допускают удаление; ошибка инспекции остаётся `unknown`. Повтор — не более одного, после остановки прежнего child. В исходном CI проверка слотов запускалась **до** `engine:fetch`; в этой редакции добавлен адресный повтор после загрузки EXE. Подтвердить фактический бинарный результат, явно отмечая пропуск там, где Windows/EXE недоступны. Автоматическое удаление PnP до этой приёмки отключено (§3.3).
- **Э0.4 — небольшой performance-проход.** Снять сопоставимые до/после в состоянии OFF, ON с видимым окном и ON в трее: CPU процесса/ядра, память, задержка UI, число status/render/log операций. Исправить только подтверждённый источник лишней работы; проверить `appendFileSync` в новом логгере и обновление больших таблиц, но не переписывать их без замера. Скрытие окна не останавливает health/fallback. Сохранить лимиты лога и существующие performance gates; бюджеты дополнительного измерения записать до изменения.

**Готово, когда:** адресные регрессии проходят, критерии Э0.1–Э0.3 проверены или явно заблокированы конкретной средой, performance-вывод опирается на замер. `NOT_RUN` живой приёмки не превращается в `DONE`. Публикация следует текущему разрешению владельца на `main`; обозначение stable определяется существующим release-контрактом отдельно.

### Э1. Довести имеющуюся диагностику «почему не открывается»

**Основание:** послойная диагностика и сравнение личных путей уже есть. Новая страница/сервис не нужны. Подтверждённые места: `probeTarget` принимает URL, `probeLayers` теряет схему/порт/путь; кнопка результата выбирает Auto, а не обязательно успешно проверенный путь.

**Где:** `validate.ts:99–106`, `layered.ts:48–67`, `index.ts:800–824`, `checker.ts`, `evidence.ts`, `netmemory.ts`, `pages/analyzer.tsx:75–79,114–115`.

- **Э1.1 — одна цель.** Разбирать URL один раз: схема, hostname/IP, порт, path/query. Direct и туннель проверяют одну цель. `http://…:8080/a` не становится HTTPS/443/`/`; `https://…:8443/a` использует нужный порт и корректный SNI. Для HTTP TLS помечен как неприменимый. Обработать IPv6 и default-port; секреты URL не попадают в отчёт. При создании доменной карточки явно показывать её область: проверенный URL не делает правило ограниченным одним path/портом.
- **Э1.2 — факты и вывод.** Сохранить послойный результат и осторожные формулировки. HTTP-ответ сам по себе не означает доступ к содержимому: различать успех, redirect, 403/405/451/5xx. HEAD 405/501 допускает один ограниченный GET либо результат «метод проверки не поддержан». Контролировать полученные байты и deadline. Измеренный успешный transport/latency не выдавать за подтверждённый HTTP 2xx через туннель, если API ядра этого не возвращает.
- **Э1.3 — применить проверенный путь.** Предлагать доступный личный ID из успешного результата `finding.via`, а не общий Auto с непроверенными участниками. При клике повторно проверить существование/отзыв профиля и актуальность результата; применить обычным механизмом карточек с ожидаемым видимым состоянием. Auto остаётся явным отдельным выбором пользователя. Диагностика не маршрутизирует сама.
- **Э1.4 — ограниченное выполнение.** Один актуальный запуск на цель/пользовательское действие, общий deadline, ограничение числа путей и отмена без оставшихся checker-процессов. Старый результат после смены сети/редактирования профиля/закрытия задачи не обновляет UI или память. Переиспользовать существующие лимиты/очереди; не создавать новый глобальный scheduler.

| Наблюдение | Допустимый вывод / действие |
|---|---|
| DNS-ответы различаются | «Ответы различаются»; учитывать CDN/балансировку. Не «подмена доказана» |
| TCP/TLS не прошёл, через другой путь цель ответила | Назвать слой и рабочий путь; возможное ограничение, причина не установлена |
| С другим SNI получилось | Это другая TLS-цель; не самостоятельное доказательство SNI-блокировки |
| С фрагментацией получилось | Этот способ помог на данной цели/сети; не универсальный диагноз DPI |
| TCP прошёл, QUIC нет | QUIC-проверка не прошла; учитывать поддержку сервера и состояние UDP |
| HTTP 451 или redirect | Показать ответ и направление; автор ограничения не определяется одним кодом |
| Все пути не ответили | «Рабочий путь не найден»; не «белый список» и не обещание исправить автоматически |

**Готово, когда:** fixtures покрывают HTTP/HTTPS, нестандартный порт/IPv6, различающиеся валидные DNS, timeout, certificate error, 405/451, успешный один личный путь при неуспешном Auto и отмену. Кнопка применяет именно предложенный путь. Контролируемый endpoint подтверждает совпадение цели; YouTube/Discord — дополнительные наблюдения из конкретной сети, не единственный oracle теста.

### Э2. Ограниченный путь «Напрямую + обход DPI»

**Зависимость:** Э0/Э1 и подтверждённая возможность закреплённого бинарника.

**Изменение:** сохранить идею четвёртого пути. В pinned engine `tls_fragment` и `tls_record_fragment` относятся к действиям `route`/`route-options`, не к обычному `direct` outbound; флаги взаимоисключающие. Сначала проверять `tls_record_fragment`; TCP-фрагментацию использовать при измеренной необходимости, поскольку она может добавлять задержку. Проверить минимальный конфиг и переключение matching rule-set выбранной карточки. Простого нового selector недостаточно. QUIC-reject, если нужен, действует только на эту карточку и удаляется при выключении режима. Не добавлять WinDivert/второй движок в рамках этого этапа.

**Готово, когда:** `sing-box check` принят, контролируемая TLS-проверка подтверждает выбранный метод, ON/OFF режима не меняет соседние карточки/PID/TUN и восстанавливает обычный Direct. Записаны накладные задержки и результат реальной сети. Если runtime не позволяет нужное live-переключение, оформить конкретный `BLOCKED`, не изображать работающую кнопку. Гарантия работы YouTube во всей РФ исключена.

### Э3. Устойчивый путь и небольшой подбор

**Зависимость:** корректные измерения Э1. Использовать существующие Auto, группы, fallback и память сети.

**Изменение:** сначала проверить переключение на уже известный рабочий личный путь с текущей защитой от колебаний. Затем ручная кнопка «Подобрать» проверяет небольшой перечисленный набор совместимых вариантов из §5; размер набора, конкуренция и общий deadline заданы до запуска. Исходник профиля сохраняется, есть отмена/откат. Память привязана к сети, цели/профилю и сроку актуальности; обновление подписки/смена сети инвалидируют неподходящий результат. Фоновое применение — только внутри явно выбранной политики пользователя.

**Готово, когда:** рабочий исходный профиль не портится; отмена, повторный вход в сеть, смена профиля и неудача всех вариантов имеют предсказуемый результат. Нет бесконечных повторов/залпов, тихого ухода в публичный путь или выдуманного статуса «IP заблокирован». Второй движок с теми же активными AWG-ключами не запускается.

### Э4. Совместимость импорта

**Изменение:** отдельными небольшими изменениями — AWG 3.1 и Hysteria2 hopping, если доступны соответствующие тестовые профили. У AWG проверить согласованные с сервером поля и маскирование нового ключа: `header_protection_key` берётся из серверного профиля и декодируется в 32 байта; при его наличии pinned engine требует `S1–S4 ≥ 12`; у HY2 учесть список/диапазон **в port part URI**, который не разбирается обычным `new URL` как одиночный числовой порт. Остальные новые протоколы — по очереди из §5, без обязательства включить их все в этот проход.

**Готово, когда для конкретного расширения:** import → сохранение/повторное чтение → outbound → `sing-box check` → адресное живое подключение; неверные ключи/диапазоны/несовместимые параметры дают понятный отказ. Старые fixtures проходят. `pqv` не объявлен работающим, значения XHTTP не вычищаются молча, REALITY defaults не меняются без доказанного дефекта. Отсутствие сервера для interop отмечается отдельно.

### Э5. Видимость без перестройки UI

**Изменение:** дополнить текущие карточки/«Подробно» и диагностику данными §7. Статус отвечает на вопросы: какой путь выбран, что применено, что измерено и когда, что не удалось проверить. Технические сведения доступны всем; dev-mode добавляет только подробности/экспорт. Неприменённые импортированные параметры видны.

**Готово, когда:** на минимальной ширине окна данные читаются, keyboard/focus работают, действующий сценарий карточек сохранён. Отчёт не содержит секретов, явный экспорт подключения отделён от отчёта; незамеренные данные не выглядят как нулевой ping/успешная проверка. `npm run test:ui` и снимок затронутого состояния — по существующему harness.

### Э6. Списки: первый полезный объём

**Изменение:** управление текущими источниками и последним валидным снимком по §6.2. Отдельный репозиторий, все форматы и локальное обучение не входят в первую поставку.

**Готово, когда:** добавить/выключить/обновить источник можно без правки TS; недоступный или повреждённый источник не стирает список, не меняет личные карточки и не публикует частичный набор. Активное обновление проходит существующее подтверждение apply; перезапуск приложения без сети сохраняет результат. Границы допустимых URL/redirect не удаляются ради произвольного источника.

### Э7. Служебная связь: кэш и понятный отказ

**Изменение:** опись текущих зависимостей, offline-start, возраст кэша, bounded обновление и разрешённый личный путь (§6.4). Подписанные mirrors/updater/аварийный набор — последующие отдельные задачи, когда определены издатель, ключи и формат.

**Готово, когда:** недоступность GitHub/каталога/одного probe-host не мешает запуску с сохранённым рабочим состоянием; пользователь видит причину и возраст данных. Рабочий файл заменяется только валидным результатом; отсутствуют бесконечные повторы и скрытое переключение на публичный хост. Новый автономный updater не является частью этого критерия.

### Э8. Публичные хосты: полезные проверяемые сведения

**Изменение:** источник, свежесть, локальная доступность и ошибки существующего каталога; точные названия проведённых проверок. Исправить дедупликацию `catalog.ts:179`: одинаковые endpoint/credentials при разных transport/path/SNI сейчас сливаются. Переиспользовать существующий `credentialKey`, сохраняя импортированные `pub-*` профили и привязки карточек. Полный рейтинг/PKI/Actions-инфраструктура отложены (§6.3).

**Готово, когда:** разные эффективные конфиги сохраняются, точные дубликаты объединяются; плохой/устаревший результат отличается от непроверенного, страна из имени не представлена измерением, публичный хост не получил метку «безопасен». Явное добавление и действующие ограничения защищённых карточек не изменены; никакая проверка не публикует личные ключи/URL.

### Общие проверки и граница завершения

Использовать существующие команды: `npm run typecheck`, `npm run check`, `npm test`, `npm run build`. При изменении UI — `npm run test:ui`; компилятора — `npm run test:performance` плюс адресный runtime-slot-сценарий; схемы протокола — проверка закреплённым engine. Новые регрессии добавляются в соответствующий существующий набор только под реальный дефект/контракт.

Live TUN-тесты выполняются на одноразовой Windows по `CONTRIBUTING.md`. CI и итоговый отчёт относятся к фактическому head, содержат пропуски; старые отчёты не переименовываются в новые. `NOT_RUN` блокирует только тот вывод/этап, для которого проверка нужна. Длинный повторный прогон требуется после изменений lifecycle, а не после редактирования этого ТЗ.

**Порядок дальше:** после первого прохода отдельно выбрать Э2, Э3 или небольшой импорт Э4; Э6/Э7/Э8 выполняются минимальными объёмами выше. Рабочие идеи не удалены, но не превращены в одну бесконечную задачу «сделать всё».

**Позже:** цепочки серверов, ПК ↔ Android, общий компилятор, языки, раздача своего хоста, Tor WebTunnel, zapret/WinDivert, развитая инфраструктура сообщества и подписанных обновлений.

**Не делаем:** собственные серверы/протоколы, Xray вторым движком, mesh, P2P-раздачу, полный kill switch, телеметрию, массовый редизайн/рефакторинг и смену зависимостей ради новизны. Это не отменяет уже существующие функции и их проверки.

**Короткий запуск задания:** «Прочитай §9 `docs/TZ-NEXT-2026-11.md`. Выполни первый проход Э0 → Э1 → Э5 на текущем коде, сохрани работающие маршруты и UI. Уже выполненное подтверди вместо повторной реализации. Справку и будущие этапы используй как контекст. Заверши отчётом по ID, проверкам и конкретным ограничениям».
