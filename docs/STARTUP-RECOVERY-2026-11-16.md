# Восстановление запуска и дополнительный аудит — 16 ноября 2026

Исходная база: `aed4e9ceaf566b57b7a87b8e821d4abde902f6a1`.

## Что подтверждено

На предоставленном скриншоте Waarp блокирует включение общей ошибкой восстановления прошлого процесса. Сам снимок не содержит журнала владельца, PID, ответа Windows или логов ядра, поэтому точную ветку отказа на том компьютере установить по нему нельзя. Аудит обнаружил несколько воспроизводимых дефектов именно на пути от первого запуска до восстановления и повторного ON.

1. Журнал старого portable-запуска сравнивал записанный путь с путём новой распаковки **раньше**, чем проверял, жив ли старый процесс. Перемещение или новая распаковка приложения могли навсегда блокировать восстановление даже при уже завершившемся PID.
2. Неуспешная первая проверка оставалась закрытым допуском на весь сеанс. Повторный ON заменял конкретную причину общим сообщением, вместо повторной проверки.
3. Поздняя фоновая проверка могла пересечься с первым ON. Проверочные ядра, основное ядро, восстановление и изменения настроек не имели одного порядка допуска.
4. Быстрый выход ядра во время записи владельца и отказ системного `spawn` обрабатывались как незавершённое восстановление. Ошибка записи владельца также могла теряться при последующей очистке.
5. Ошибка удаления временного конфига могла потерять запись владельца, необходимую для повторной очистки.
6. Portable-перезапуск с UAC мог использовать временный внутренний EXE, а старый экземпляр мог закончить очистку уже после записи состояния новым. Общая папка распаковки одного билда создавала ещё один независимый конфликт.
7. Проверка прав через `net session` зависела от службы Server; это не эквивалент проверки elevated-токена. Обёртка PowerShell могла принять JSON из stdout после неуспешного завершения команды.

## Изменения

### Владение и восстановление

- Восстановление сопоставляет **PID, полный исходный путь и время создания процесса**. Новый путь приложения не отменяет доказанную принадлежность старого процесса. Совпадение одного имени или PID не даёт права завершать процесс.
- Нечитаемая/повреждённая запись и неизвестная идентичность остаются отдельными отказами. Удаление повреждённой записи допускается только после подтверждённого отсутствия всех процессов соответствующего имени; завершение посторонних процессов по имени не применяется.
- Конфиг удаляется до записи владельца. Если очистка не удалась, следующий запуск сохраняет возможность повторить её.
- Восстановление имеет состояния `recovering`, `ready`, `failed`, объединяет параллельные обращения и допускает повторную попытку после отказа.
- Стартовая проверка резервирует место в очереди до регистрации управляющего IPC. Открытие окна не ждёт сетевой проверки; запуск ядра ждёт её результата.
- Результат OFF отменяет старое намерение ON сразу. Позднее окончание подготовки не открывает закрытый пользователем туннель.
- Ошибки восстановления, неизвестный процесс, запись владельца, очистка и ошибка запуска ядра сохраняют разные диагностические сообщения.

### Перезапуск приложения

- Для portable используется стабильный `PORTABLE_EXECUTABLE_FILE`.
- Повышенный экземпляр ждёт подтверждённого завершения родителя до открытия хранилища, моста и журналов. Ожидание ограничено по времени; таймаут не считается успехом.
- Старая копия удерживает singleton-блокировку во время UAC и завершения; повышенная получает её только после выхода родителя и до общих файлов. Обычный третий запуск во время диалога повышения прав не может войти в shared state. Отмена UAC сохраняет блокировку старой копии.
- Установлен `build.portable.unpackDirName: true` для фактически используемого `electron-builder 26.15.3`. Обоснование по исходникам конкретной версии и расхождение с описанием параметра изложены в [аудите lifecycle](UPSTREAM-LIFECYCLE-2026-11-16.md).
- Проверка администратора читает текущий Windows-токен и ограничена по времени. PowerShell с ненулевым завершением или таймаутом не даёт успешный результат даже при наличии JSON в stdout.

### Сетевые проверки и измерения

Ошибка чтения адаптеров больше не означает пустую сеть без конфликтов. Перед запуском требуется полный снимок; периодическая проверка уже работающего соединения показывает предупреждение при временном отказе чтения. Измеритель при неполной проверке не получает разрешение использовать потенциально занятый адрес.

Исправлена история состояния при вращающихся пакетах измерений: временное отсутствие профиля в текущем пакете больше не обнуляет его последовательные ошибки. История удаляется при удалении профиля из действительного состава. Ноль миллисекунд принимается как корректная округлённая задержка; отрицательные и нечисловые значения не считаются успешным ответом. Неудача одного пакета не объявляет все загруженные туннели недоступными.

Основание для сравнения: [sing-box URLTest, commit `a8e5963`](https://github.com/SagerNet/sing-box/blob/a8e5963aa834d64bbe9a1ddc0d33d9140da5af51/common/urltest/urltest.go) хранит историю по тегу и возвращает целые миллисекунды. В Waarp реализовано собственное исправление; исходный GPL-код не переносился в Apache-2.0 приложение.

## Интерфейс

Во время восстановления интерфейс показывает подготовку, после отказа — конкретную причину и действия «Повторить запуск»/«Восстановить Waarp». Восстановление процессов сохраняет профили и маршруты и оставляет главный переключатель выключенным. Ошибки больше не сопровождаются зелёной галочкой успеха. Намерение владельца и фактический статус ядра отображаются раздельно.

## Порядок и границы проверки

После уточнения пользователя дополнительный проход выполняется в порядке **сравнение исходников → исправления → тесты**. Реальный конфиг хранится отдельно от репозитория, не попадает в тестовые фикстуры, CI, отчёты или артефакты сборки.

Подготовлены независимые уровни проверки:

1. Офлайн-регрессии состояния и отрицательных сценариев. Мок процесса в таком тесте не считается настоящим запуском ядра.
2. Windows CI с реальными безопасными дочерними процессами: идентичность PID/путь/время, перенос пути, завершение, ожидание родителя. Эти тесты не создают TUN.
3. DOM-проверки production-сборки интерфейса в Chromium и сохранение снимков.
4. Linux-запуск закреплённого настоящего ядра с предоставленным AWG2-профилем в userspace, без системного TUN. Проверка локального API отдельно от прохождения трафика через удалённый сервер.
5. Полный системный TUN, Wintun, маршруты Windows и сон физического Windows-компьютера требуют соответствующей среды. Отсутствие `/dev/net/tun` и `CAP_NET_ADMIN` здесь не подменяется фиктивным успешным результатом.

Фактические результаты исполнения публикуются в отдельном отчёте после завершения проверок.
