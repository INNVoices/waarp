# Desktop: маршруты, полезная передача и служебные загрузки

Аудит продолжает текущую архитектуру Waarp. Визуальная система и модель карточек сохранены. Основа проверки — production-код `apply.ts`, `engine.ts`, `awg.ts`, `checker.ts` и обработчики IPC в `index.ts`.

## Исправленные причины перезапуска и отключения

1. Удаление или выключение последней активной карточки раньше могло трактоваться как отсутствие потребности в VPN и остановка всего ядра. Теперь общий выключатель владеет сессией: существующий TUN остаётся включённым, включая переход всех карточек в Direct. Если пользователь сам выключил Waarp, редактирование только сохраняет настройки.
2. Переход Direct → профиль менял не только селектор, но и статическую конфигурацию DNS/IPv6. Общий маршрут, DNS-назначения, IPv6-отказы и обход `.ru` вынесены в подтверждаемые локальные rule-set файлы; топология уже загруженных объектов остаётся стабильной.
3. Загруженные профили сохраняют порядок независимо от сортировки библиотеки. Неактивные карточки не вытесняют активные маршруты из существующего пула слотов. Неиспользуемая новая группа не добавляет native-объекты посреди сессии. Выбранный участник загруженной группы сохраняется при её выключении и возвращении.
4. Равенство сохранённых настроек больше не выдаётся за факт применения. Сравнение и повторная попытка опираются на последний подтверждённый runtime. После ошибки UI показывает неподтверждённый маршрут как ожидающий применения, даже если новый профиль отвечает на отдельный ping.
5. DNS-приоритет теперь соответствует приоритету карточек, включая пересекающиеся домены, Direct, отсутствующий профиль и приложение перед доменным правилом. Порядок импорта серверов не меняет владельца DNS-запроса.

## Транзакция изменения маршрута

Порядок применения: временный reject-барьер для затронутых новых соединений → подтверждение загрузки барьера → смена селекторов с чтением `now` → новые rule-set файлы и индивидуальные DNS witness ACK → закрытие только соединений изменённых правил → подтверждённое снятие барьера → публикация runtime-состояния.

Успешный HTTP-код селектора сам по себе недостаточен. Для каждого PUT выполняется GET, подтверждающий фактически выбранный tag. Для rule-set файлов используется отдельный непредсказуемый DNS witness; ответ старой версии файла не подтверждает новую.

Ошибка ACK, выбора, закрытия соединения или снятия барьера не превращается в перезапуск TUN. Система пытается вернуть старые селекторы и файлы под барьером. Если восстановление не подтверждено, сессия VPN сохраняется, ошибка остаётся видимой, состояние не считается применённым. Повторное действие сначала согласует незавершённую транзакцию. Отдельный пользовательский OFF прерывает работу и имеет приоритет.

Барьер действует на новые решения маршрутизации; он не закрывает все существующие соединения. Отдельно проверяется сохранение соседнего долгоживущего потока. При полном отказе native API нельзя выдавать неподтверждённое состояние барьера за доказанную блокировку — сообщение прямо говорит о неподтверждённом состоянии маршрутов.

## Граница горячего применения

В начале сессии подготавливается ограниченный пул личных lazy-профилей: до 64 профилей и 16 endpoint-объектов, с приоритетом ссылок из настроек. Обязательные активные профили сохраняются сверх этого лимита. Публичный каталог не прогревается. OpenVPN, AWG с hostname bootstrap, положительным keepalive или уже используемой парой ключей не запускаются скрыто ради будущего выбора.

Переключение между уже загруженными совместимыми профилями, добавление/удаление/перестановка карточек в пределах слотов и изменение общего маршрута применяются без пересоздания ядра. Новый незагруженный профиль, изменение ключей/протокола, новая native-топология или исчерпание слотов остаются структурным изменением. Это отдельная контролируемая реконфигурация; данная работа не заявляет hot-add для произвольного native outbound.

Причина ограничения: закреплённый desktop core предоставляет Clash API для выбора существующих объектов; полноценного создания outbound через него нет. Основание для сверки: [pinned core proxies API](https://github.com/Leadaxe/sing-box-lx/blob/3d3d3db3a2ccef3b1a8eb71b831ed2461c54b94d/experimental/clashapi/proxies.go) и [configs API](https://github.com/Leadaxe/sing-box-lx/blob/3d3d3db3a2ccef3b1a8eb71b831ed2461c54b94d/experimental/clashapi/configs.go).

## Проверка полезной передачи

В анализатор добавлена отдельная ручная проверка выбранного личного профиля. При включённом VPN используется тот же core; при выключенном — эксклюзивная аренда существующего checker. Второй конкурирующий процесс поверх работающего VPN не запускается. Локальный HTTP inbound слушает только `127.0.0.1`, требует случайные credentials и использует отдельный селектор, не меняющий карточки.

Контрольная загрузка: `https://www.rfc-editor.org/rfc/rfc6455.txt`, ровно **162067 байт**, SHA-256 **`765775326aee0ecca9b04bde3fd1f52932d498e33e34e428bd61b8a24da0fa3b`**. Проверяются полный размер и хеш; короткий ответ, перенаправление, подменённый HTML или оборванная загрузка успехом не считаются. Это проверка конкретного адреса и передачи тела, а не утверждение о скорости/доступности всего интернета.

Отправка выполняется только на явно введённый пользователем HTTPS endpoint. Тело — 65536 байт ASCII с повторением `waarp-payload-v1\n`; сервер должен вернуть JSON `{ "bytes": 65536, "sha256": "<SHA-256 полученного тела>" }`. Без endpoint результат — «не измерено». Общий срок проверки ограничен 60 секундами. TLS-сертификат и имя сервера проверяются; перехода на Direct нет.

Помощник совместимых настроек использует ту же полную контрольную загрузку. Ответ на HEAD/204 больше не квалифицирует вариант как доказанно рабочий. Исходный профиль не изменяется автоматически. В persisted-результат не попадают URL отправки, тела ответов, локальные proxy credentials или конфиги.

## Загрузки подписок, списков и каталога

В настройках есть отдельный `serviceVia`: Direct по умолчанию либо доступный личный профиль. Выбор не меняет пользовательские маршруты и сам по себе не перезапускает TUN. Загружаются подписки, списки доменов и источники каталога; для всего батча каталога удерживается один выбранный путь.

При выборе профиля DNS тоже проходит через него: bounded DoH A/AAAA к `cloudflare-dns.com`, bootstrap CONNECT к `1.1.1.1`, обязательная проверка TLS-имени. Локальный DNS не используется как запасной путь. Каждый ответ проверяется существующим запретом private ranges; IP HTTP-соединения закрепляется за проверенным ответом, а SNI/Host остаются исходными. Каждый redirect повторно проходит проверку URL, адресов и allowlist каталога. Документированные endpoints и JSON schema сверены с [Cloudflare network operators](https://developers.cloudflare.com/1.1.1.1/infrastructure/network-operators/) и [DoH JSON](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-https/make-api-requests/dns-json/).

Недоступный профиль, DNS/HTTP/TLS-ошибка, отмена или неподтверждённое завершение checker сохраняют прежние данные. Нет автоматического Direct retry. Удаление профиля учитывает его использование для загрузок; без выбранной замены ссылка остаётся недоступной до явного изменения настройки.

## Проверки на этой итерации

| Проверка | Что действительно проверяет |
|---|---|
| `route-lifecycle.check.ts` | Реальные `createApply`/`Engine` с моделируемым native I/O: успешная смена, соседние соединения, последняя карточка, все стадии отказа, rollback, повтор после незавершённого rollback, OFF fences |
| `route-switch-matrix.check.ts` | 20 переходов компилятора и границы ограниченного preload |
| `routing-dns-priority.check.ts` | 37 независимых семантических DNS-решений; полный runtime из списка 50k доменов и 200 карточек |
| `diagnostic-owner.check.ts` | Реальные методы Engine/Checker и локальный HTTP API fixture: no-op PUT не открывает Direct, readback, эксклюзивный владелец, отмена |
| `payload.check.ts` | Настоящие локальные CONNECT и TLS-соединения с проверяемым сертификатом, точная отправка/receipt, неверный hostname, авторизация, лимиты, truncation, redirect refusal, отмена |
| `service-download.check.ts` | Production-пути подписок/списков/каталога при poisoned local DNS, selected-profile DoH, private/truncated ответы, pinning, redirects, cache, удаление профиля, отмена |
| `route-native.check.ts` | Явный Windows CI opt-in с закреплённым бинарником: actual HTTP body A/B, соседний TCP-поток, PID/since, удаления/добавления, последняя карточка и authenticated diagnostic CONNECT |

В локальной Linux-среде прошли `typecheck`, статические проверки, **46/46 offline suites**, production build main/preload/renderer и `git diff --check`. Windows/TUN проверки отмечены как пропущенные, их нельзя считать пройденными по этим результатам.

Измерение именно watched-rule компилятора: 50k доменов + 200 карточек — **2 310 493 байта rule-set файлов**, **175 мс** в локальном запуске. Prefix index не копирует большой список в каждое следующее непересекающееся DNS-правило. Это синтетический контроль размера/компиляции, не измерение скорости VPN.

Native gate запускается после получения и проверки закреплённого Windows core, до portable-сборки: `WAARP_NATIVE_SWITCH_TEST=1 node out/test/route-native.check.js`. Итоговый CI run и проверка APK/portable фиксируются в общем build audit на фактически публикуемом commit.
